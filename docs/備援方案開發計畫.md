# 備援方案開發計畫

本文件整理「出門過夜」與「電腦故障」兩種風險下的備援方案。目標不是把完整 SaaS 立刻搬上雲端，而是先確保最重要的每日決策不中斷，並讓完整系統與資料可以從雲端還原。

## 一、核心目標

1. 即使主電腦關機、故障、Docker 無法啟動，也要能取得 SOXL #21 參數的每日市場狀態，尤其是「基準模型目標權重」。
2. 即使 Yahoo 或自動抓資料失敗，也要能手動輸入最新收盤價，保存資料，並算出當日結果。
3. 所有重要資料要有雲端備份；換新電腦後，可以從 GitHub 與雲端備份還原完整系統。
4. 備援工具不得引入交易功能，不保存交易所憑證，不讓策略核心依賴 I/O、網路、時間或資料庫。

## 二、三層四工具總覽

| 層級 | 工具 | 解決問題 | 是否需要網路 | 主要資料 |
|---|---|---|---|---|
| 第一層 | Go 緊急試算工具 | 主系統不能開時，仍能手動輸入 SOXL 收盤價並算出 #21 目標權重 | 不需要 | #21 參數包、SOXL 日線收盤價、手動新增收盤價 |
| 第一層 | 單檔 HTML/PWA | 手邊只有手機或瀏覽器時，也能做最低限度試算 | 不需要，首次取得檔案後可離線 | 匯入的備援資料包、瀏覽器本機資料 |
| 第二層 | GitHub Actions 每日自動試算 | 主電腦不開也能每天自動抓 SOXL 日線並產生結果 | 需要 | 輕量備援資料包、最新日線、每日結果 |
| 第三層 | 雲端備份與還原工具 | 電腦故障後還原完整 SaaS 與資料 | 備份/還原時需要 | PostgreSQL 全量備份、增量行情資料、設定資料 |

## 三、第一層：緊急每日 SOXL 試算

### 工具一：Go 緊急試算工具

建立一個獨立命令列工具，例如 `cmd/emergency-signal`。它只處理「#21 SOXL 日線參數」的緊急試算，不啟動前端、不啟動 Postgres、不需要 Docker。

功能範圍：

1. 從目前資料庫匯出 SOXL #21 參數與必要日線資料，形成備援資料包。
2. 在沒有資料庫時，讀取備援資料包進行試算。
3. 允許手動輸入新的 SOXL 收盤價，寫入本機資料檔。
4. 輸出最新市場狀態、基準模型目標權重、相對前一個交易日的目標權重變化。
5. 提供純文字與 JSON 輸出，方便人看，也方便 GitHub Actions 或 PWA 使用。

預計指令形式：

```powershell
quantsaas-emergency export --instrument SOXL --parameter-id 21 --out emergency/soxl-21.bundle.json
quantsaas-emergency calc --bundle emergency/soxl-21.bundle.json --date 2026-06-22 --close 28.34
quantsaas-emergency latest --bundle emergency/soxl-21.bundle.json
```

資料檔設計：

| 檔案 | 用途 |
|---|---|
| `emergency/soxl-21.bundle.json` | 參數、標的、週期、執行假設、歷史日線收盤價與版本資訊 |
| `emergency/soxl-21-manual-prices.jsonl` | 手動補上的每日收盤價 |
| `emergency/soxl-21-latest.json` | 最新一次試算結果 |
| `emergency/soxl-21-latest.md` | 人類可讀的最新結果摘要 |

一致性要求：

1. 試算必須呼叫現有策略/回測計算邏輯，不能在 CLI 裡另外寫一套不同算法。
2. 策略核心仍保持純計算；讀檔、寫檔、時間、網路都只存在 CLI 外層。
3. 需要加測試：同一組資料下，CLI 算出的基準模型目標權重要與 SaaS 市場狀態頁一致。

### 工具二：單檔 HTML/PWA

建立一個最低限度的離線頁面，例如 `emergency/soxl-21.html`。用途是手機或任意瀏覽器可開，手動輸入收盤價後取得試算結果。

功能範圍：

1. 匯入 `soxl-21.bundle.json`。
2. 手動新增每日收盤價。
3. 將新增資料存在瀏覽器本機儲存空間。
4. 可匯出更新後資料，避免手機遺失或瀏覽器清除資料後全丟。
5. 顯示最新日期、收盤價、市場狀態、基準模型目標權重、目標權重變化。

風險與處理方式：

1. Go CLI 是計算真源，PWA 是便利備援。
2. 若 PWA 需要在 JavaScript 端鏡像策略計算，必須建立 golden fixture 測試，確保輸出與 Go CLI 一致。
3. 若策略邏輯變動，必須重新產生 PWA 或更新測試 fixture。

## 四、第二層：GitHub Actions 每日自動試算

建立 GitHub Actions workflow，定時執行輕量試算，而不是啟動完整 SaaS。

預計流程：

1. 排程在美股收盤後執行。
2. 下載或讀取 SOXL 備援資料包。
3. 嘗試抓取最新 SOXL 日線資料。
4. 呼叫 `quantsaas-emergency latest` 產生最新結果。
5. 將結果保存為 artifact，或提交到指定備援分支/目錄。
6. 若抓資料失敗，workflow 明確失敗，提醒改用第一層手動輸入。

安全限制：

1. 如果 GitHub repo 是公開的，不應直接公開 #21 完整參數包。
2. 預設做法是使用私有 repo，或將參數包加密後再交給 Actions 使用。
3. 不放任何交易所 API key，因為此工具只做資料與試算，不做交易。

## 五、第三層：雲端備份與還原

### 工具四：備份/還原工具

備份目的不是每天同步整個 Docker 環境，而是讓資料可靠、還原步驟簡單。

備份策略：

1. 每日增量備份：只備份當天新增或變更的行情資料與必要研究資料。
2. 每週全量備份：匯出完整 PostgreSQL 備份，作為可靠還原錨點。
3. 手動全量備份：提供一個明確指令或按鈕，讓使用者在想保險時自行執行。

不採用「重大操作前後自動全量備份」作為第一版，避免自動機制太複雜。第一版只保留每日增量、每週全量、手動全量三種。

預計備份內容：

| 類型 | 內容 |
|---|---|
| 全量備份 | PostgreSQL `pg_dump`、必要環境設定範本、備份索引 |
| 增量備份 | 新增 K 線、商品清單變更、參數庫新增/更新、採用參數狀態 |
| 不備份 | Docker image、node_modules、暫存檔、交易所憑證 |

雲端目標：

1. 第一版可先輸出到本機 `backups/`。
2. 第二版接 rclone，上傳到 Google Drive、OneDrive 或 Dropbox。
3. 上傳前先壓縮與加密；雲端只保存加密檔。

還原流程目標：

1. 新電腦安裝 Git、Docker。
2. 從 GitHub clone 專案。
3. 下載最近一次每週全量備份。
4. 套用該全量備份之後的每日增量備份。
5. 啟動 Docker compose，登入後看到原本資料、參數庫、採用參數與行情資料。

## 六、開發階段

### 階段一：Go 緊急試算工具

完成項目：

1. 建立 `cmd/emergency-signal`。
2. 匯出 SOXL #21 備援資料包。
3. 支援手動輸入收盤價並保存。
4. 支援最新結果輸出。
5. 加入一致性測試，確認與市場狀態頁計算結果一致。

驗收標準：

1. 關掉 SaaS 與資料庫後，仍能用備援資料包算出 SOXL 最新目標權重。
2. 手動輸入新收盤價後，再次執行會讀到剛剛輸入的資料。
3. 同一歷史日期的輸出與 SaaS 市場狀態頁一致。

### 階段二：單檔 HTML/PWA

完成項目：

1. 建立離線頁面。
2. 支援匯入/匯出備援資料包。
3. 支援手動輸入收盤價。
4. 顯示最新狀態與目標權重。
5. 加入與 Go CLI 對照的 fixture。

驗收標準：

1. 不開 Docker、不連網也能開頁面。
2. 手動輸入資料後重新整理頁面，資料仍存在。
3. PWA 與 Go CLI 在 fixture 上輸出一致。

### 階段三：GitHub Actions 每日自動試算

完成項目：

1. 建立 scheduled workflow。
2. 使用輕量 Go CLI 取得最新 SOXL 結果。
3. 保存每日結果。
4. 抓資料失敗時提供清楚錯誤。

驗收標準：

1. 手動觸發 workflow 可成功產生最新結果。
2. GitHub 上能看到最新結果摘要或下載 artifact。
3. 失敗時不會產生假結果。

### 階段四：備份與還原

完成項目：

1. 建立每日增量備份指令。
2. 建立每週全量備份指令。
3. 建立手動全量備份指令。
4. 建立還原指令與還原說明。
5. 後續接 rclone 上傳雲端。

驗收標準：

1. 可從空資料庫還原最近一次全量備份。
2. 可在全量備份後套用增量備份。
3. 還原後，行情資料、商品清單、參數庫、採用參數狀態一致。

## 七、優先順序

1. 先做 Go 緊急試算工具，因為它直接解決「今天一定要知道 SOXL 目標權重」。
2. 再做 PWA，讓手機或臨時電腦也能最低限度操作。
3. 再做 GitHub Actions，自動化每日 SOXL 試算。
4. 最後做完整備份/還原，並逐步接雲端儲存。

## 八、第一版不做的事

1. 不新增交易功能。
2. 不把完整 SaaS 強行塞進 GitHub Actions。
3. 不在公開 repo 暴露敏感參數包。
4. 不把策略核心改成會讀檔、寫檔或連網。
5. 不讓備份系統保存任何交易所憑證。
