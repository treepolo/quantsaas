# 研究功能規格討論流程

> 文件定位：本文件規定研究功能從想法到完整開發指導文件的討論方式。
>
> 狀態：現行流程，自 2026-07-13 起適用；使用者可隨時要求修訂。
>
> 適用範圍：`docs/研究構想整理/` 內尚未完成的字母大點、既有項目的追加討論，以及其他涉及量化定義、研究方法、搜尋機制、回測語義或重大功能的新討論。
>
> 本文件不是三份真源文件，也不批准任何尚未確認的新功能實作。

## 一、流程目標

本流程用來避免以下問題：

- Agent 連續提出大量簡短問題，卻未說明為什麼需要決定。
- 將需要數學、統計或金融背景的判斷直接丟給使用者選擇。
- 只列出選項名稱，沒有解釋各選項如何運作、優缺點與後果。
- 尚未理解問題便被迫作答，之後又必須反覆追問與推翻決定。
- 討論途中引入新的概念，卻沒有區分既有知識、Agent 建議與已確認規格。
- 一次討論過多互不相依的問題，造成疲勞、遺漏與前後矛盾。
- 討論完成後才發現輸入、公式、邊界、保存、測試或依賴關係仍未定義。

討論的責任分工如下：

- 使用者負責確認研究目的、實際想觀察的現象、可接受的行為與最終產品語義。
- Agent 負責補足必要知識、查證專業主張、提出完整方案、比較取捨、給出明確建議，並承擔一般技術設計判斷。
- 需要專業背景才能回答的問題，不得在缺乏解釋與建議時直接要求使用者選擇。

## 二、基本原則

### 2.1 不提出裸問題

不得只問「要 A 還是 B」、「門檻是多少」、「這個怎麼定義」或一串沒有上下文的短問題。

每個需要使用者決定的問題，都必須包裝成一個完整的「決策單元」，先讓使用者具備作答所需資訊，再提出明確決策點。

### 2.2 一次只處理一個主要決策

每則討論訊息原則上只包含：

- 一個主要決策；以及
- 最多兩個只有在主要決策下才能回答、且彼此緊密相依的子決策。

互不相依的問題必須拆到後續訊息。不得因為它們都屬於同一字母大點，就一次全部列給使用者回答。

### 2.3 先解釋，再建議，最後才詢問

討論順序固定為：

1. 說明為什麼現在需要處理這個問題。
2. 補足理解問題所需的背景知識。
3. 說明各方案實際如何運作。
4. 比較各方案的影響、優點、缺點與風險。
5. Agent 提出自己的建議與理由。
6. 最後才指出使用者真正需要決定的內容。

### 2.4 Agent 必須提出判斷

Agent 不得把所有選項平鋪後以「看你想要哪個」結束。除非證據確實不足或選項純屬個人偏好，否則必須提出推薦方案，並說明推薦所依據的研究目的、數學意義、專案現況與工程取捨。

如果沒有足夠資訊形成建議，Agent 必須先查證或明確說明缺少什麼，而不是假裝所有選項同樣合理。

### 2.5 專業主張要區分證據層級

討論內容必須清楚區分：

- **已知事實**：可由數學定義、既有程式、專案文件或可靠研究來源支持。
- **合理推論**：由已知條件推導，但仍需實證驗證。
- **設計提案**：為滿足本專案需求而提出，尚未由使用者確認。
- **已確認規格**：使用者已明確同意，後續文件與開發必須遵守。

涉及學術研究、業界慣例、統計性質或容易隨時間變動的資訊時，Agent 應先查閱可靠來源並交代研究結論及限制，不得只以「一般都這樣做」代替論證。

### 2.6 不重問已決定事項

提出新問題前，Agent 必須先檢查：

- 使用者是否已在先前訊息中回答。
- 既有研究文件是否已有明確結論。
- 是否能由已確認規格直接推導。
- 是否只是低階實作細節，可由 Agent 依專案慣例決定。

若新想法會推翻既有結論，必須明確指出衝突與受影響文件，不得把舊決定當作從未存在。

## 三、決策單元的強制內容

每個決策單元必須包含以下內容；可依問題複雜度調整篇幅，但不得省略其意義。

### 3.1 決策主題

用一句話說清楚這次只要決定什麼，不混入下一個問題。

### 3.2 為什麼需要決定

說明這項決定在整個功能中的用途，以及不決定會卡住哪一段規格。若它其實不影響使用者可見行為，也不影響研究語義，就不應要求使用者決定。

### 3.3 回答所需的背景知識

Agent 必須用不預設數學、統計或金融學位的方式說明必要概念，包括：

- 名詞的白話定義。
- 它實際測量或控制什麼。
- 它不代表什麼，避免名稱造成誤解。
- 與使用者原始問題的關係。

### 3.4 方案如何運作

每個可行方案都要描述實際輸入、處理與輸出，不能只給名詞。必要時使用與本專案相關的具體例子，例如費半、SOXL、一天與二十日行情。

### 3.5 不同決策的影響與優劣

至少檢查與本題有關的下列面向：

- 是否真的回答原研究問題。
- 數學或統計意義是否清楚。
- 是否會偷看未來或造成資料洩漏。
- 是否能跨商品、跨期間比較。
- 是否增加過擬合自由度。
- 對搜尋空間、計算量與保存量的影響。
- 對回測、實盤一致性與既有結果的影響。
- 使用者日後能否理解、檢查與重現結果。
- 實作複雜度與後續擴充限制。

只有確實相關的面向需要展開，但不得省略會改變結論的重要缺點。

### 3.6 Agent 的建議

Agent 必須說明：

- 推薦哪個方案。
- 為什麼最符合使用者已表達的研究目的。
- 哪些部分有充分依據，哪些仍屬待驗證假設。
- 若推薦組合方案，組合中的每個部分各自解決什麼問題。

不得先提出改進方案，再在同一段自行推翻，卻不給出清楚結論。

### 3.7 使用者真正需要回答的內容

最後以一個清楚、可用自然語言回答的問題收束。使用者可以：

- 採納 Agent 建議。
- 選擇其他方案。
- 修改方案。
- 表示尚未理解並要求繼續解釋。
- 暫緩此題。

不得要求使用者使用固定格式作答，也不得把「我不知道」視為無效回答；使用者不知道時，Agent 應繼續分析並縮小決策範圍。

## 四、數學與量化內容的解釋標準

只要決策涉及公式、指標、機率、統計量、評分或搜尋方法，Agent 必須依下列順序解釋：

1. **先說目的**：這個量要解決什麼問題。
2. **再說白話意思**：不看公式時，它代表什麼。
3. **逐一定義符號**：每個變數的來源、時間點、單位與可用時間。
4. **給簡單數字例子**：展示輸入改變時結果怎麼變。
5. **說明為何適合**：它如何對應使用者想觀察的現象。
6. **說明限制與反例**：什麼情況下它會失真或回答另一個問題。
7. **比較替代方案**：替代方案衡量的是什麼，為何採用或不採用。
8. **標明狀態**：這是既有定義、候選公式，還是已確認公式。

公式不能只因形式漂亮而採用。若公式依賴假設，例如常態分佈、獨立性、固定視窗或平方根時間法則，必須把假設及不成立時的影響一起說明。

## 五、哪些決定應由誰負責

### 5.1 必須由使用者確認

- 功能究竟要回答哪個研究問題。
- 指標或狀態在產品中的實際語義。
- 會改變回測、參數搜尋、成交或績效解讀的公式。
- 可由使用者調整的範圍與行為。
- 不同方案都合理、但反映不同研究偏好的取捨。
- 會讓既有保存結果失效或改變含義的重大變更。

### 5.2 Agent 應直接承擔並說明

- 可由現有架構與專案慣例決定的程式模組切分。
- 不改變研究語義的資料結構、API、快取與內部命名。
- 一般錯誤處理、輸入驗證、取消、進度與版本保存方式。
- 已有明確專案規範可遵循的 UI 與工程細節。
- 可以透過檢查程式或文件直接查明的現況。

Agent 不得把缺乏把握的技術問題偽裝成產品偏好丟回使用者；應先調查，再把真正會影響使用者的部分提出來。

## 六、單一字母大點的討論階段

討論順序與最終開發順序無關。每個字母大點原則上依下列階段進行：

### 階段 0：恢復脈絡

- 重讀原始構想、先前結論與相關文件。
- 列出本項已決定、尚未決定、已取消與移到其他字母的內容。
- 說明本輪要處理的範圍，不立即丟出整份問題清單要求回答。

### 階段 1：研究目的與完成品邊界

- 功能要回答什麼問題。
- 使用者最後會看到或操作什麼。
- 哪些內容明確不屬於本功能。

### 階段 2：資料、定義與因果時間

- 輸入資料及其可用時間。
- 預測目標、觀測量與名詞定義。
- 避免未來資料洩漏的時間順序。
- 跨商品、跨頻率與缺值語義。

### 階段 3：數學機制與狀態行為

- 候選公式及其意義。
- 狀態如何開始、延續、切換與結束。
- 邊界值、樣本不足與異常資料處理。

### 階段 4：搜尋、調整與限制

- 哪些數值由使用者設定、由電腦搜尋或固定不變。
- 搜尋空間、限制條件與可解釋性要求。
- 評分、抗過擬合與穩健性驗證方式。

### 階段 5：操作、結果與保存

- 頁面或共用模組如何被使用。
- 輸出圖表、統計與比較方式。
- 任務、設定、資料版本、結果與快取如何保存及重用。
- 大量計算的總計算量、進度、取消與恢復。

### 階段 6：依賴、測試與完成定義

- 與既有功能及其他字母大點的依賴關係。
- 合理開發順序，但不把討論順序誤當開發順序。
- 單元測試、整合測試、回歸測試與可驗收案例。
- 哪些條件全部成立後才能稱為完成。

### 階段 7：總結與落文件

- Agent 先完整重述已確認結論與未決項目。
- 使用者確認沒有遺漏或誤解後，才整理成對應開發指導文件。
- 文件須標明依賴、禁止事項、測試要求及是否仍有待討論內容。

上述階段可以因內容相依而來回修正，但不得跳過仍會影響功能語義的問題。

## 七、每輪討論後的結論管理

每完成一個決策單元，Agent 必須在回覆中簡短標示：

- **已確認**：可寫入開發指導文件的內容。
- **暫定**：目前採用，但仍依賴後續問題。
- **待討論**：尚未作決定。
- **取消**：明確不做。
- **移出本項**：保留想法，但歸入其他字母或文件。

若使用者只是在理解概念、尚未表態，不得自行把 Agent 建議記為已確認。

討論過程中發現會影響已存在文件的結論時，Agent 必須指出：

- 受影響的文件。
- 原本內容。
- 新結論將如何修改。
- 是否需要立即補文件，或等本項完整討論後再統一整理。

不得默默覆蓋舊結論。

## 八、疲勞與岔題控制

- 使用者表示看不懂時，下一則回覆只處理不懂的部分，不順便加入新的決策。
- 新想法若不妨礙當前決策，先記入待討論清單，完成當前決策後再回來。
- 新想法若推翻當前前提，先停止原問題，解釋衝突後重新定位。
- 不因為 Agent 已規劃後續大綱，就提前要求使用者回答尚未具備背景的問題。
- 同一概念若使用者已連續追問，Agent 應改用數字例子、反例、流程或圖示，不得只換同義詞重講。
- 使用者可以隨時要求「只整理目前結論」、「先不要問下一題」或「把這題暫停」，Agent 必須遵守。

## 九、討論完成判定

一個字母大點只有在下列項目皆已確認，或被明確標記為不適用、延期到指定項目時，才能稱為「討論完成」：

- 研究目的與功能邊界。
- 使用者操作流程與輸出。
- 輸入資料、時間語義與資料可用性。
- 名詞、指標、公式及單位。
- 狀態轉換、邊界與例外行為。
- 可設定值、可搜尋值、搜尋範圍與限制。
- 評分、驗證與抗過擬合機制。
- 計算量、進度、取消、快取與結果保存。
- 與既有系統及其他開發文件的依賴。
- 回歸風險、測試方式與完成定義。
- 所有未決問題均已有明確去向。

只有概念、欄位、頁面骨架或候選公式時，不得宣稱討論完成，也不得進入實作。

## 十、標準決策單元範本

後續實際對話應採自然語言，不必機械式逐欄填表，但內容必須等價涵蓋：

```text
本輪決策：要決定的唯一主要問題

為什麼現在要決定：
這會影響哪一段功能；不決定會卡住什麼。

先理解必要概念：
用白話、公式符號定義與數字例子補足作答所需知識。

方案與實際運作：
A 如何運作。
B 如何運作。
必要時說明組合方案或不做此功能的結果。

影響比較：
研究意義、資料洩漏、跨商品、過擬合、計算量、實作與使用上的差異。

Agent 建議：
明確推薦及理由，並標示仍需實證的部分。

這次請使用者決定：
只留下真正需要確認的一個問題；可以直接採納建議、修改或要求進一步解釋。

本輪狀態：
已確認 / 暫定 / 待討論 / 取消 / 移出本項。
```

## 十一、與既有專案規則的關係

- 本流程服從根目錄 `AGENTS.md`、`CLAUDE.md` 與 `docs/重大更新開發守則.md`。
- 新研究功能仍須留在獨立文件，不得寫入三份既有穩定系統真源文件。
- 本流程只規定如何把需求討論清楚，不代表任何候選公式或功能已獲准實作。
- 正式開發前仍須依對應開發指導文件確認範圍、依賴、測試與完成定義。
