# 重大更新開發守則

**文件定位：** 本文件是 Agent 執行重大更新、分階段開發、架構改造與研究模型改動時的強制工作守則。它不取代三份真源文件，而是規定「怎麼開發、怎麼回報、什麼不能宣稱完成」。

## 1. 適用範圍

以下情況必須先讀本文件：

- 影響策略數學、參數搜尋、回測、市場狀態、行情資料或參數庫語義的改動。
- 多資產、外部指標、特徵層、資料集建構器、進化引擎等重大研究升級。
- 任何分階段開發、MVP、原型、相容層或暫時方案。
- 任何可能讓既有參數結果、回測結果、備援試算結果改變的改動。

## 2. 真源層級

本專案既有穩定系統的需求真源仍是：

- `docs/系統總體拓撲結構.md`
- `docs/策略數學引擎.md`
- `docs/進化計算引擎.md`

其他計畫文件、討論文件與本守則只能補充工作方式。新功能、重大更新、研究草案、MVP 範圍與未確認規格必須寫在獨立 `docs/` 文件，不得直接寫入三份真源文件。若尚未確認，必須標記為「待討論」或「不得實作」。

## 3. 階段完成定義

不得把以下狀態稱為「完成」：

- 只有資料欄位、API 通道或 UI 選項，但核心邏輯尚未完整接上。
- 只有 MVP、骨架、暫時公式、測試替身或相容 shim。
- 只驗證 happy path，尚未補回歸測試或未說明測試缺口。
- 文件要求尚未落地，或落地內容與文件語義不同。

每個階段回報時必須使用其中一種狀態：

- `已完成`：定義範圍全部完成，測試通過，已知缺口不影響該階段定義。
- `部分完成`：已有可用片段，但還不能稱為該階段完成。
- `未完成`：尚未開始或主要功能未落地。
- `暫停待討論`：需要使用者確認規格後才能繼續。

## 4. MVP 規則

預設不做 MVP。只有在架構風險高、需要先驗證核心契約或使用者明確同意時，才可做 MVP。

若需要 MVP，寫程式前必須先向使用者明確說明：

- 為什麼這次需要 MVP。
- MVP 包含哪些功能。
- MVP 不包含哪些功能。
- 使用者應該測試什麼。
- 測試通過後，哪些功能必須補齊，階段才可稱為完成。
- 這個 MVP 是否沿用最終架構，或只是會被刪除的暫時原型。

MVP 必須建立在預計保留的最終架構上。不得為了看起來能跑，臨時發明與真源文件無關、之後必須刪除的量化公式、特徵聚合或參數機制，除非使用者事前明確批准。

若不是 MVP，開工前要說明「本階段採一次到位」，並列出該階段完成定義。

## 5. 禁止臨場發明量化邏輯

不得自行新增真源文件沒有定義、使用者也未確認的量化邏輯，例如：

- 任意 z-score、百分位、移動平均、斜率、比率或標準化公式。
- 任意把多個外部序列平均、加權、投票或壓縮成單一訊號。
- 任意新增閾值、懲罰、權重、基因欄位或限制。
- 任意改變基準模型、實務模型、成交過濾、成本、資料可用時間或回測語義。

若文件只寫方向，尚未定義公式、metadata、欄位、邊界、可用時間或評分方式，必須停下來回報「規格不足」，不要先猜。

## 6. 外部序列與特徵層守則

同一個序列可在不同任務中被選為交易商品或外部參考，但外部參考不是單一神祕訊號。完整設計至少需要：

- 明確的 `FeatureSpec` 或等價規格，描述每個特徵的來源、轉換、視窗、頻率、缺值規則與 `available_at`。
- 每個特徵的 metadata，讓 UI 與回測能知道它代表什麼、何時可用、是否可交易。
- 明確的參數搜尋空間：哪些特徵可被選、哪些權重或開關可演化、邊界是什麼。
- 避免過度擬合的機制，例如特徵數量懲罰、out-of-sample 或 walk-forward。
- 與既有單商品策略的回歸測試，確保未選外部特徵時舊結果不變。

外部序列細節在使用者確認前，不能把任何「單商品 + 外部指標」階段宣稱完成。

- 沒有完整 FeatureSpec、FeatureMatrix、metadata、缺值規則與可用時間語義。
- 沒有每個外部序列或每個特徵的可演化控制。
- 沒有完成特徵數量懲罰、out-of-sample 或對應穩健性保護。

- 之後必須決定現有暫時通道是移除、停用，還是重構進正式 FeatureSpec 路徑。
- 後續任何回報都必須把「技術通道可運作」與「完整功能完成」分開說明。

## 8. 開工與收工回報格式

重大階段開工前，回報至少包含：

- 本階段是一次到位或 MVP。
- 本階段完成定義。
- 本階段不做什麼。
- 需要讀取或更新哪些真源文件。
- 預計測試方式與風險。

重大階段收工時，回報至少包含：

- 狀態：已完成 / 部分完成 / 未完成 / 暫停待討論。
- 完成清單與未完成清單。
- 測試結果。
- 任何可能影響既有研究結果的語義變更。
- 下一步是否需要使用者確認。

## 9. 文件優先

若實作途中發現規格不足、文件衝突或需求語義不清，必須先回報並補文件，不得先用程式碼猜。若已經寫出與文件不一致的暫時實作，必須標記為暫時、不宣稱完成，並提出移除或重構計畫。

## 10. 新功能文件隔離

三份真源文件不得作為新功能草案區。所有新功能都必須先建立或更新獨立文件，例如 `docs/<功能名稱>開發計畫.md`、`docs/<功能名稱>規格草案.md` 或既有對應草案文件。

獨立文件必須清楚標示：

- 文件定位：草案、討論稿、開發計畫或使用說明。
- 是否已由使用者確認。
- 哪些內容可實作，哪些仍待討論。
- 是否為 MVP，以及 MVP 之後還缺什麼。

Agent 不得因為某段內容被寫進真源文件就假設它已被使用者批准；若發現真源文件混入未確認新功能段落，必須先移出或回報，不得繼續擴寫。
