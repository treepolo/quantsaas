# 進化計算引擎

**文件目標：** 將進化系統降維為純粹尋優黑盒。進化引擎不關心具體策略內部結構，只透過抽象介面驅動種群生命週期。

---

## 第 0 章：核心定位

進化引擎是一個純計算執行緒：接收策略提供的基因空間、歷史 K 線資料集與進化設定，對種群執行多代搜尋，最後交付最優基因集。

引擎不知道策略內部訊號公式、倉位三態語義、特定時鐘機制，也不 import 任何具體策略實作。引擎只知道基因是一個可採樣、可修復、可驗證、可交叉、可變異、可評分的不透明載體。

輸出結果一律先以 `challenger` 角色寫入資料庫，等待人工 Promote 成為 `champion`。進化任務不得自動改變實盤參數。

---

## 第 1 章：探索窗口定義

### 1.1 多時段坩堝

Epoch 啟動時，引擎一次性從資料庫拉取本 Epoch 所需的全部歷史 K 線，用來構造四個評估窗口。不對全庫長度設人工上限；長週期窗口以已入庫的最早可用 bar 至最新 bar 為準。

| 窗口 | 評分區間 | 權重 |
|---|---|---:|
| `10y` | 全量歷史，實際可長於十年 | 0.40 |
| `5y` | 最近 1825 天 | 0.30 |
| `2y` | 最近 730 天 | 0.20 |
| `6m` | 最近 183 天 | 0.10 |

短窗口在評分區間前可預留最多 1200 天 warmup K 線，用於指標預熱但不計入分數。嚴禁未來資料洩漏：每個窗口的評分區間從 `EvalStartMs` 開始，warmup 必須早於 `EvalStartMs`。

### 1.2 基因空間語義操作

策略向引擎提供三個基因空間操作：

- `Sample`：從合法空間隨機生成基因。
- `Clamp`：修復越界基因，包含欄位硬邊界與結構約束。
- `Validate`：檢查修復後基因是否合法。

引擎不直接讀取欄位名稱，也不理解欄位語義。新增策略只要實作同一組語義操作即可接入進化流程。

### 1.3 出生點凍結

`quant.SpawnPoint` 代表 Epoch 級出生點，包含資金政策、風險邊界與實例上下文。它在 Epoch 啟動時固定，全種群共享，不參與代內交叉變異，也不進入基因組指紋。

`POST /api/v1/evolution/tasks` 支援 `spawn_mode`：`inherit`、`random_once`、`manual`。`manual` 必須帶 `spawn_point` JSON，並由 service 層驗證合法性。

## 第 2 章：進化生命週期動作

### 2.1 種群初始化

種群大小預設 `Population = 300`。若資料庫中存在精英基因，初始化分配如下：

- 10%：從資料庫精英原樣拷貝。
- 40%：在精英基礎上施加加性高斯強化變異。
- 50%：完全隨機生成。

若資料庫無精英，索引 0 使用產品預設冠軍染色體，其餘個體完全隨機生成。索引 0 永遠保留目前種子冠軍原樣，作為可比較基線。

### 2.2 並發適應度評估

評估使用固定大小 worker pool：

```text
Workers = min(NumCPU, PopulationSize)
```

每個 worker 獨占一份 backtest adapter，不共享可變狀態。所有個體評估完成後，才進入選擇、交叉與變異。

### 2.3 錦標賽選擇

每次選擇從種群中隨機抽取 `TournamentSize` 個體，預設為 3，取適應度最高者作為父代。fatal 個體因分數極低，會自然被淘汰，不需額外排除。

### 2.4 均勻交叉

Uniform Crossover 對每個基因維度以 50% 機率從父代 A 或父代 B 選取。交叉後必須呼叫策略提供的 Clamp 修復越界值與結構約束。

引擎不理解欄位語義，因此不能針對特定策略寫交叉規則。若策略需要欄位相依修復，必須封裝在策略的 Clamp 或 Crossover 實作內。

### 2.5 加性高斯變異

每個基因維度以獨立 Bernoulli 機率 `MutationProbability` 決定是否變異，預設 `0.15`。變異量為：

```text
Normal(0, 1) × GeneStep × MutationScale
```

變異後呼叫 Clamp 修復。`MutationScale` 預設 `1.0`，可由變異斜坡調整。

### 2.6 精英保留

每代保留適應度 Top `EliteCount` 個體，預設 8，不經交叉變異直接進入下一代。精英保留保證最佳解不因隨機操作倒退。

### 2.7 收斂檢測與變異斜坡

連續 `EarlyStopPatience` 代最佳分數改善低於 `EarlyStopMinDelta` 時，放大變異概率與幅度：

```text
MutationProbability *= 1.25
MutationScale       *= 1.25
```

上限為 `MutationProbabilityMax = 0.55`、`MutationScaleMax = 3.0`。當變異參數觸及上限後仍無改善，才觸發 Early Stop。

### 2.8 基因組指紋快取

策略提供 `Fingerprint`，以 FNV-1a-64 與 1e-6 精度生成基因指紋。Epoch 內若指紋命中快取，直接復用評估結果，跳過重複回測。

快取只在單一 Epoch 內有效，不作跨任務真源。預期可降低精英保留與交叉造成的重複評估。

### 2.9 結果交付

進化正常完成或 Early Stop 後，將最佳基因透過 `EncodeResult` 編碼為 JSON，寫入 `GeneRecord`，角色為 `challenger`。

進化任務本身不 Promote，也不改變實盤實例。人工審核是從研究結果到實盤參數的必要閘門。

## 第 3 章：適應度黑盒

### 3.1 多窗口分數

每個窗口先計算策略相對 Ghost DCA 的 Alpha：

```text
Alpha = ROI_strategy - ROI_GhostDCA
SliceScore = Alpha - 1.5 × max(0, MaxDD_strategy - MaxDD_GhostDCA)
```

若 `MaxDD_strategy >= 0.88`，該窗口 `SliceScore = -99999`，視為 fatal 硬否決。

總分：

```text
ScoreTotal = 0.40 × Score_10y
           + 0.30 × Score_5y
           + 0.20 × Score_2y
           + 0.10 × Score_6m
```

### 3.2 Ghost DCA 基準

Ghost DCA 以出生點種子資本買入標的資產，之後每個自然月月初將月度注資全額買入。它是被動定投對照組，策略必須跑贏它才有實用價值。

Ghost DCA 與策略使用相同價格序列、相同注資節奏與相同評分窗口，避免基準偏差。

### 3.3 ROI 計算

ROI 採 Modified Dietz 思路，剔除注資時刻對 NAV 的跳變影響。注資不是收益，只有注資後資產價值變化才算入策略表現。

最大回撤基於淨資產曲線計算，並與 Ghost DCA 最大回撤比較，超額回撤會被懲罰。

### 3.4 級聯短路

適應度評估按 `6m → 2y → 5y → 10y` 順序執行。一旦某窗口 fatal，立即返回 fatal 分數並跳過後續長窗口。

短路能大幅節省早期代的計算量，因為高風險染色體通常會在短窗口先暴露災難性回撤。

## 第 4 章：`EvolvableStrategy` 八動詞契約

| 動詞 | 職責 |
|---|---|
| `StrategyID()` | 回傳策略唯一識別 |
| `Sample(rng)` | 隨機生成合法基因 |
| `Mutate(c, prob, scale, rng)` | 施加加性高斯變異 |
| `Crossover(p1, p2, rng)` | 交叉兩個父代，產生子代 |
| `Fingerprint(c)` | 生成基因指紋 |
| `Evaluate(ctx, c, plan)` | 在坩堝計畫上評估基因 |
| `DecodeElite(json)` | 從 DB 參數包解碼精英基因 |
| `EncodeResult(c, spawn)` | 將結果序列化為參數包 JSON |
| `Verify(ctx, c, spawn, bars, lotStep, lotMin)` | 額外驗證路徑，規劃但可延後 |

引擎以 `Gene = any` 持有基因，不讀取內部欄位。具體策略新增欄位時，不得修改通用引擎。

## 第 5 章：`EvaluablePlan` 只讀上下文

`EvaluablePlan` 在 Epoch 啟動時建構，整個世代內不可變，傳給所有 `Evaluate` 呼叫。

```text
EvaluablePlan
├── Pair, TemplateName
├── Spawn *quant.SpawnPoint
├── LotStep, LotMin
├── Windows []CrucibleWindow
├── DCABaselines []DCABaseline
└── AggregateCache
```

DCA 基線在 Epoch 啟動時一次性預計算。各染色體評估直接讀取，不重複跑 Ghost DCA。

## 第 6 章：結果交付與基因角色三態

基因角色形成狀態機：

| 角色 | 含義 |
|---|---|
| `challenger` | 進化產出，等待人工審批 |
| `champion` | 目前活躍冠軍，供實盤或新實例使用 |
| `retired` | 歷史冠軍，只供查閱與回溯 |

Promote 必須在資料庫交易中完成：

1. 目前 `champion` 改為 `retired`。
2. 指定 `challenger` 改為 `champion`，記錄啟用時間。
3. 刪除 Redis `champion:{strategyID}` 快取。

Promote 完成後，下次 cron tick 會自動載入新的 champion。

## 第 7 章：HTTP 觸發契約

### `POST /api/v1/evolution/tasks`

建立進化任務，僅允許 `app_role` 為 `lab` 或 `dev`。

| 參數 | 預設 | 範圍 | 說明 |
|---|---:|---:|---|
| `pop_size` | 300 | [10, 500] | 種群大小 |
| `max_generations` | 25 | [5, 50] | 最大代數 |
| `spawn_mode` | `inherit` | `inherit` / `random_once` / `manual` | 出生點來源 |
| `spawn_point` | null | JSON | `manual` 時必填 |
| `test_mode` | false | bool | 快速測試，Pop=10、Gen=3 |

### `GET /api/v1/evolution/tasks`

回傳目前任務狀態、是否運行中、歷史任務清單、最新 challenger、目前 champion 與各窗口分數摘要。

### 規劃但未實作

WFO 推進式滾動測試、定時自動觸發 GA、Nested Replay、前綴和滑窗統計與 Monte Carlo 非同步化都屬於規劃項目，不進入當前最小可用範圍。
