# 開發操作手冊

本文件是給 AI coding agent 與使用者共同遵守的操作手冊。目標是避免每次開發都重新踩同一批終端機、Docker、編碼與重啟問題。

## AI 指導文件層級

本專案的文件層級如下：

1. `docs/系統總體拓撲結構.md`、`docs/策略數學引擎.md`、`docs/進化計算引擎.md`
   - 產品與系統需求真源。
   - 若程式與文件衝突，以這三份文件為優先。

2. `AGENTS.md`
   - 給所有 coding agent 的專案總規則。
   - 包含：先讀文件、正體中文輸出、不得建立 SQL migration、不得把憑證寫入 SaaS/DB/UI/測試。

3. `CLAUDE.md`
   - 更詳細的專案開發規範。
   - 與 `AGENTS.md` 不可衝突；若衝突，先停下來回報。

4. `.agents/skills/*.md`
   - 特定領域的補充指引，不等同於 `AGENTS.md`。
   - 例如 Go 後端、部署維運、量化數學、系統架構。

5. `docs/開發操作手冊.md`
   - 固定命令入口與環境操作手冊。
   - 用來解決 PowerShell 轉義、Docker config、UTF-8 亂碼、測試超時、重啟太慢等反覆問題。

## 固定入口原則

AI agent 與使用者都應優先使用 `scripts/dev/` 與根目錄 `.bat`，不要每次手動拼長命令。

原因：

- PowerShell 容易把 `$env:DOCKER_CONFIG` 吃掉。
- 未指定 Docker config 時，Docker 可能去讀 `C:\Users\...\ .docker\config.json` 並遇到權限錯。
- 長命令容易因引號、空白、中文路徑而失敗。
- `docker compose up -d --build` 很穩，但日常啟動不需要 build，會浪費 1 到 3 分鐘。
- 固定腳本會統一處理 UTF-8、Docker Desktop 喚醒、Docker engine 等待、Go cache 與工作目錄。

## 使用者日常入口

根目錄提供以下 `.bat`，可直接雙擊：

- `啟動軟體.bat`
  - 日常開機後使用。
  - 會嘗試喚醒 Docker Desktop，等待 Docker engine 可用，然後執行 `docker compose up -d`。
  - 不會重新建置，通常比開發用 rebuild 快很多。
  - 啟動後會開啟 `http://localhost:8080`。

- `重啟軟體.bat`
  - 只重啟 SaaS 容器。
  - 適合服務卡住但程式碼沒有變的情況。

- `重新建置並啟動.bat`
  - 會執行 `docker compose up -d --build`。
  - 只有在程式碼改動後，需要套用新版本時使用。

- `查看服務狀態.bat`
  - 顯示 Postgres、Redis、SaaS 容器狀態。

## AI 開發固定入口

AI agent 應優先使用以下 PowerShell 腳本：

- `scripts/dev/compose-up.ps1`
  - 啟動服務，不 build。

- `scripts/dev/compose-restart.ps1`
  - 重啟 SaaS 容器，不 build。

- `scripts/dev/compose-rebuild.ps1`
  - 重新建置並啟動。
  - 只有 Go 後端、前端、Dockerfile、設定檔等改動需要套用時使用。

- `scripts/dev/compose-build.ps1`
  - 只重新建置映像，不啟動或重啟任何服務。
  - 需要驗證容器建置、但本次工作不得連線或異動資料庫時使用。

- `scripts/dev/compose-ps.ps1`
  - 查看容器狀態。

- `scripts/dev/go-test.ps1`
  - 預設跑 `go test ./internal/... -count=1`。
  - 可用 `-Target ./cmd/...` 或 `-Target ./internal/saas/marketdata` 指定範圍。

- `scripts/dev/go-fmt.ps1`
  - 使用 Docker 內 Go 版本格式化指定 Go 檔案。

- `scripts/dev/frontend-build.ps1`
  - 執行 `npm run build`。

## 常用範例

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev\compose-up.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev\compose-ps.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev\compose-build.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev\compose-rebuild.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev\go-test.ps1 -Target ./internal/...
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev\frontend-build.ps1
```

## 何時需要 build

不需要 build：

- 使用者日常開軟體。
- 只是重啟容器。
- 只是查看狀態。

需要 build：

- Go 後端程式碼有改。
- 前端程式碼有改。
- `Dockerfile`、`docker-compose.yml`、`config.yaml` 等影響容器映像或啟動行為的檔案有改。

## 終端機陷阱

1. 不要手動拼巢狀 PowerShell + Docker 長命令。
2. 不要直接裸跑 `docker compose ...`，除非已明確設定 `DOCKER_CONFIG`。
3. 不要用 `go test ./...` 當第一輪驗證；先跑較小範圍，再視需要擴大。
4. 讀中文檔案若終端機顯示亂碼，不要據此判斷檔案內容錯誤；先用固定腳本或編輯器確認 UTF-8。
5. 若只是套用已建好的服務，不要使用 `--build`。

## Docker／WSL 記憶體異常處理

若執行大量研究後網頁持續轉圈、取消無回應，且工作管理員顯示 `VmmemWSL` 佔用大量記憶體：

1. 不要在工作管理員強制結束 `VmmemWSL`；它是 Docker Desktop 使用的 WSL2 虛擬機程序，可能顯示存取被拒。
2. 先從 Docker Desktop 停止引擎，或使用正常的 Docker／WSL 關閉流程；確認服務停止後再處理程式問題。
3. 不要立刻重開尚未修正的可恢復任務，否則計算 worker 會接續未完成項目。
4. 本機 compose 預設限制 SaaS 為 4 GB、PostgreSQL 為 3 GB、Redis 為 512 MB，Go heap 軟上限為 3 GiB；可用 `SAAS_MEMORY_LIMIT`、`POSTGRES_MEMORY_LIMIT`、`REDIS_MEMORY_LIMIT`、`GOMEMLIMIT` 覆寫，但不得取消日誌輪替。
5. 重開後以服務狀態、任務狀態及容器記憶體觀察確認穩定，再讓大型研究續跑。

## 後續維護

若之後又遇到新的固定環境問題，優先更新：

1. `scripts/dev/common.ps1`
2. 相關 `scripts/dev/*.ps1`
3. 本文件
4. 必要時更新 `AGENTS.md`

不要只在對話裡記錄問題，否則下一次仍會重新踩坑。
