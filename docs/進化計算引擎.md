# 進化計算引擎

**文件目標：** 將進化系統降維為純粹尋優黑盒。進化引擎不關心具體策略內部結構，只透過抽象介面驅動種群生命週期。

---

## 第 0 章：核心定位

進化引擎是一個純計算執行緒：接收策略提供的基因空間、歷史 K 線資料集、研究標的、執行假設與進化設定，對種群執行多代搜尋，最後交付最優基因集。

引擎不知道策略內部訊號公式、倉位三態語義、特定時鐘機制，也不 import 任何具體策略實作。引擎只知道基因是一個可採樣、可修復、可驗證、可交叉、可變異、可評分的不透明載體。

輸出結果一律先以 `challenger` 角色寫入資料庫，等待人工 Promote 成為該研究標的的 `champion`。進化任務不得自動改變實盤參數。

所有任務、基因與已採用參數必須依 `strategy_id + instrument_id + interval + data_source + execution_mode` 隔離。不同標的、不同資料來源或不同執行假設下產生的參數不得互相覆蓋。

## 第 1 章：探索窗口定義

### 1.1 多時段坩堝

Epoch 啟動時，引擎一次性從資料庫拉取本 Epoch 所需的歷史 K 線，用來構造四個評估窗口。任務可指定 `train_start` 與 `train_end`；若指定，所有評估窗口只能使用該範圍內資料。未指定時，長週期窗口以已入庫的最早可用 bar 至最新 bar 為準。

| 窗口 | 評分區間 | 權重 |
|---|---|---:|
| `10y` | 全量歷史，實際可長於十年 | 0.40 |
| `5y` | 最近 1825 天 | 0.30 |
| `2y` | 最近 730 天 | 0.20 |
| `6m` | 最近 183 天 | 0.10 |

短窗口在評分區間前可預留最多 1200 天 warmup K 線，用於指標預熱但不計入分數。嚴禁未來資料洩漏：每個窗口的評分區間從 `EvalStartMs` 開始，warmup 必須早於 `EvalStartMs`。

### 1.2 基因空間語義操作

策略向引擎提供三個基因空間操作：

- `Sample`：從合法空間隨機生成基因。
- `Clamp`：修復越界基因，包含欄位硬邊界與結構約束。
- `Validate`：檢查修復後基因是否合法。

引擎不直接讀取欄位名稱，也不理解欄位語義。新增策略只要實作同一組語義操作即可接入進化流程。

### 1.3 出生點凍結

`quant.SpawnPoint` 代表 Epoch 級出生點，包含資金政策、風險邊界與實例上下文。它在 Epoch 啟動時固定，全種群共享，不參與代內交叉變異，也不進入基因組指紋。

`POST /api/v1/evolution/tasks` 支援 `spawn_mode`：`inherit`、`random_once`、`manual`。`manual` 必須帶 `spawn_point` JSON，並由 service 層驗證合法性。

### 1.4 研究執行假設

日 K 研究必須明確指定 `execution_mode`，並且參數搜尋、回測與市場狀態判讀需使用同一個假設：

| execution_mode | 說明 |
|---|---|
| `close_same_bar` | 使用當日 close 產生訊號，假設同一根日 K close 可調倉 |
| `close_next_open` | 使用當日 close 產生訊號，以下一交易日 open 作為執行價 |
| `preclose_10m` | 使用收盤前 10 分鐘快照產生訊號，假設接近收盤前調倉 |

第一版不得把三種模式混成同一個適應度函數。應以單一 `execution_mode` 搜尋參數，完成後可用其他 `execution_mode` 做交叉回測。`preclose_10m` 只能在具備歷史快照資料的區間使用，不得用不存在的快照假裝長期回測。

## 第 2 章：進化生命週期動作

### 2.1 種群初始化

種群大小預設 `Population = 300`。若資料庫中存在精英基因，初始化分配如下：

- 10%：從資料庫精英原樣拷貝。
- 40%：在精英基礎上施加加性高斯強化變異。
- 50%：完全隨機生成。

若資料庫無精英，索引 0 使用產品預設冠軍染色體，其餘個體完全隨機生成。索引 0 永遠保留目前種子冠軍原樣，作為可比較基線。

### 2.2 並發適應度評估

評估使用固定大小 worker pool：

```text
Workers = min(NumCPU, PopulationSize)
```

每個 worker 獨占一份 backtest adapter，不共享可變狀態。所有個體評估完成後，才進入選擇、交叉與變異。

### 2.3 錦標賽選擇

每次選擇從種群中隨機抽取 `TournamentSize` 個體，預設為 3，取適應度最高者作為父代。fatal 個體因分數極低，會自然被淘汰，不需額外排除。

### 2.4 均勻交叉

Uniform Crossover 對每個基因維度以 50% 機率從父代 A 或父代 B 選取。交叉後必須呼叫策略提供的 Clamp 修復越界值與結構約束。

引擎不理解欄位語義，因此不能針對特定策略寫交叉規則。若策略需要欄位相依修復，必須封裝在策略的 Clamp 或 Crossover 實作內。

### 2.5 加性高斯變異

每個基因維度以獨立 Bernoulli 機率 `MutationProbability` 決定是否變異，預設 `0.15`。變異量為：

```text
Normal(0, 1) × GeneStep × MutationScale
```

變異後呼叫 Clamp 修復。`MutationScale` 預設 `1.0`，可由變異斜坡調整。

### 2.6 精英保留

每代保留適應度 Top `EliteCount` 個體，預設 8，不經交叉變異直接進入下一代。精英保留保證最佳解不因隨機操作倒退。

### 2.7 收斂檢測與變異斜坡

連續 `EarlyStopPatience` 代最佳分數改善低於 `EarlyStopMinDelta` 時，放大變異概率與幅度：

```text
MutationProbability *= 1.25
MutationScale       *= 1.25
```

上限為 `MutationProbabilityMax = 0.55`、`MutationScaleMax = 3.0`。當變異參數觸及上限後仍無改善，才觸發 Early Stop。

### 2.8 基因組指紋快取

策略提供 `Fingerprint`，以 FNV-1a-64 與 1e-6 精度生成基因指紋。Epoch 內若指紋命中快取，直接復用評估結果，跳過重複回測。

快取只在單一 Epoch 內有效，不作跨任務真源。預期可降低精英保留與交叉造成的重複評估。

### 2.9 結果交付

進化正常完成或 Early Stop 後，將最佳基因透過 `EncodeResult` 編碼為 JSON，寫入 `GeneRecord`，角色為 `challenger`。

進化任務本身不 Promote，也不改變實盤實例。人工審核是從研究結果到實盤參數的必要閘門。

若任務被取消，狀態必須寫為 `cancelled`。若任務尚未產生任何可驗證的目前最佳參數，則不得產生候選參數；若任務已在監控快照中留下目前最佳參數，取消收尾時可將該參數保存為 `challenger`，並在 `search_config` 標記來源為取消任務。GA loop、個體評估、窗口評估與回測 adapter 必須定期檢查 context cancellation。

## 第 3 章：適應度黑盒

### 3.1 多窗口分數

每個窗口先計算實務模型策略相對 Ghost DCA 的 Alpha：

```text
Alpha = ROI_strategy - ROI_GhostDCA
SliceScore = Alpha - 1.5 × max(0, MaxDD_strategy - MaxDD_GhostDCA)
           - TradePenalty × TradeCount_strategy
```

若 `MaxDD_strategy >= 0.88`，該窗口 `SliceScore = -99999`，視為 fatal 硬否決。

`TradePenalty` 由參數搜尋頁設定，預設為 `0`。`TradeCount_strategy` 指實務模型在該窗口中實際執行的買賣意圖次數；若調倉門檻擋下微觀調倉，該次不計入交易次數。Ghost DCA 基準仍使用同一組手續費與滑價設定，但交易次數懲罰只懲罰策略側，以降低過度調倉的搜尋偏好。

總分：

```text
ScoreTotal = 0.40 × Score_10y
           + 0.30 × Score_5y
           + 0.20 × Score_2y
           + 0.10 × Score_6m
```

### 3.2 Ghost DCA 基準

Ghost DCA 以出生點種子資本買入標的資產，之後每個自然月月初將月度注資全額買入。它是被動定投對照組，策略必須跑贏它才有實用價值。

Ghost DCA 與策略使用相同價格序列、相同注資節奏與相同評分窗口，避免基準偏差。

策略側 `ROI_strategy` 與 `MaxDD_strategy` 必須使用實務模型淨值曲線。實務模型每日仍呼叫同一套 `Step()` 取得基準模型目標權重，但只有當實務持倉權重與基準模型目標權重的差距達到染色體內的 `RebalanceThreshold` 時，才在指定 `execution_mode` 的執行時間進行微觀調倉。`RebalanceThreshold = 0` 表示不啟用額外調倉門檻。進化任務可透過 `evolve_rebalance_threshold` 選擇是否讓此欄位進入採樣、交叉與變異；未啟用時所有候選基因的該欄位固定為 0。

### 3.3 ROI 計算

ROI 採 Modified Dietz 思路，剔除注資時刻對 NAV 的跳變影響。注資不是收益，只有注資後資產價值變化才算入策略表現。

最大回撤基於淨資產曲線計算，並與 Ghost DCA 最大回撤比較，超額回撤會被懲罰。

### 3.4 級聯短路

適應度評估按 `6m → 2y → 5y → 10y` 順序執行。一旦某窗口 fatal，立即返回 fatal 分數並跳過後續長窗口。

短路能大幅節省早期代的計算量，因為高風險染色體通常會在短窗口先暴露災難性回撤。

## 第 4 章：`EvolvableStrategy` 八動詞契約

| 動詞 | 職責 |
|---|---|
| `StrategyID()` | 回傳策略唯一識別 |
| `Sample(rng)` | 隨機生成合法基因 |
| `Mutate(c, prob, scale, rng)` | 施加加性高斯變異 |
| `Crossover(p1, p2, rng)` | 交叉兩個父代，產生子代 |
| `Fingerprint(c)` | 生成基因指紋 |
| `Evaluate(ctx, c, plan)` | 在坩堝計畫上評估基因 |
| `DecodeElite(json)` | 從 DB 參數包解碼精英基因 |
| `EncodeResult(c, spawn)` | 將結果序列化為參數包 JSON |
| `Verify(ctx, c, spawn, bars, lotStep, lotMin)` | 額外驗證路徑，規劃但可延後 |

引擎以 `Gene = any` 持有基因，不讀取內部欄位。具體策略新增欄位時，不得修改通用引擎。

## 第 5 章：`EvaluablePlan` 只讀上下文

`EvaluablePlan` 在 Epoch 啟動時建構，整個世代內不可變，傳給所有 `Evaluate` 呼叫。

```text
EvaluablePlan
├── Pair, TemplateName
├── Spawn *quant.SpawnPoint
├── LotStep, LotMin
├── Windows []CrucibleWindow
├── DCABaselines []DCABaseline
└── AggregateCache
```

DCA 基線在 Epoch 啟動時一次性預計算。各染色體評估直接讀取，不重複跑 Ghost DCA。

## 第 6 章：結果交付與基因角色三態

基因角色形成狀態機：

| 角色 | 含義 |
|---|---|
| `challenger` | 進化產出，等待人工審批 |
| `champion` | 目前活躍冠軍，依研究標的組合唯一 |
| `retired` | 歷史冠軍，可查閱、回測，也可重新設為 champion |

Promote 必須在資料庫交易中完成：

1. 同一 `strategy_id + instrument_id + interval + data_source + execution_mode` 下目前 `champion` 改為 `retired`。
2. 指定 `challenger` 或 `retired` 改為 `champion`，記錄啟用時間。
3. 刪除 Redis `champion:{strategyID}` 快取。

Promote 完成後，下次 cron tick 會自動載入新的 champion。

未採用的 `challenger` 可刪除或封存；`challenger`、`champion`、`retired` 都必須可回測。

## 第 7 章：研究回測輸出契約

研究回測除了淨值曲線與 Ghost DCA 基準外，還必須輸出下列序列：

1. 實務模型目標權重每日值。
2. 實務模型目標權重每日變化值。
3. 基準模型目標權重每日值。
4. 基準模型目標權重每日變化值。
5. 空倉參考目標權重每日值。
6. 空倉參考目標權重每日變化值。

基準模型目標權重指實務模型路徑每日呼叫 `Step()` 後產生的理論目標，並由 SaaS 後端把 `Step()` 的目標浮動倉位加上當下宏觀底倉與封存資產曝險，轉成總倉位比例後提供給 UI。回測策略淨值則使用實務模型：從回測起點以空倉與出生點資金開始，依同一套 `Step()`、同一組參數與同一個 `execution_mode` 逐日推進，但微觀調倉需通過 `RebalanceThreshold` 後才執行。實務模型目標權重指調倉門檻後實際採用的總倉位目標；若未觸發調倉門檻，該值沿用前一次採用值，不得因價格漂移或實際持倉比例變化而自行改變。空倉參考指每一日獨立假設帳戶全現金、浮動倉位為 0，只用截至該日的價格序列呼叫同一套 `Step()` 得到參考目標權重；因為此參考帳戶沒有既有宏觀底倉，總倉位比例等同該日參考目標。

三種序列的每日變化皆為今日總倉位比例減昨日總倉位比例。第一筆沒有昨日值時，變化為 0。`RebalanceThreshold` 的觸發判斷仍使用微觀浮動倉權重差距，不使用總倉位比例。

回測圖表互動要求：

1. 淨值圖、實務模型目標權重圖、實務模型目標權重變化圖、基準模型目標權重圖、基準模型目標權重變化圖、空倉參考目標權重圖與空倉參考目標權重變化圖使用同一個時間範圍。
2. 游標所在日期需同步顯示於所有圖表。
3. 下方拖拉滑塊控制所有圖表共同的顯示起點與終點。
4. Tooltip 至少顯示策略淨值、Ghost DCA 淨值、淨值日變化、實務模型目標權重、實務模型目標權重變化、基準模型目標權重、基準模型目標權重變化、空倉參考目標權重、空倉參考目標權重變化。

## 第 8 章：HTTP 觸發契約

### `POST /api/v1/evolution/tasks`

建立進化任務，僅允許 `app_role` 為 `lab` 或 `dev`。

| 參數 | 預設 | 範圍 | 說明 |
|---|---:|---:|---|
| `pop_size` | 300 | [10, 500] | 種群大小 |
| `max_generations` | 25 | [5, 50] | 最大代數 |
| `spawn_mode` | `inherit` | `inherit` / `random_once` / `manual` | 出生點來源 |
| `spawn_point` | null | JSON | `manual` 時必填 |
| `test_mode` | false | bool | 快速測試，Pop=10、Gen=3 |
| `instrument_id` | `BTCUSDT` | 允許清單 | 研究標的 |
| `data_source` | 依標的 | `binance` / `yahoo` | 資料來源 |
| `interval` | `1d` | 依標的限制 | 非 BTC 只允許日 K |
| `execution_mode` | `close_same_bar` | 見 1.4 | 研究執行假設 |
| `evolve_rebalance_threshold` | false | bool | 是否讓調倉門檻作為核心參數參與採樣、交叉與變異；false 時固定為 0 |
| `evolve_force_full_threshold` | false | bool | 是否讓強制滿倉門檻參與採樣、交叉與變異；false 時固定為 1 |
| `evolve_force_empty_threshold` | false | bool | 是否讓強制空倉門檻參與採樣、交叉與變異；false 時固定為 0 |
| `enable_w_mean` | true | bool | 是否啟用均值回歸訊號；false 時 `WMean` 固定為 0 |
| `enable_w_momentum` | true | bool | 是否啟用動能訊號；false 時 `WMomentum` 固定為 0 |
| `enable_w_breakout` | true | bool | 是否啟用突破訊號；false 時 `WBreakout` 固定為 0 |
| `position_structure` | `dual_layer` | enum | `dual_layer` 表示宏觀底倉 + 微觀浮動倉；`floating_only` 表示純浮動模型，宏觀底倉與底倉釋放相關 6 個參數不參與演化 |
| `trade_penalty` | 0 | number | 每次實務模型交易的評分懲罰，評分時扣除 `trade_penalty × 交易次數` |
| `train_start` | null | 日期 | 訓練資料起點 |
| `train_end` | null | 日期 | 訓練資料終點 |

### `GET /api/v1/evolution/tasks`

回傳目前任務狀態、是否運行中、歷史任務清單、最新 challenger、目前 champion 與各窗口分數摘要。

任務進行中可回傳「本次任務目前最佳」監控資料，包含暫時最佳分數、最大回撤、各窗口分數與參數包預覽。這些資料只代表目前任務內的暫時領先個體；任務正常完成或 Early Stop 後，最終最佳基因才會透過 `GeneRecord` 以 `challenger` 角色寫入資料庫。任何 `challenger` 都必須經人工 Promote 才能成為 `champion`。

### `GET /api/v1/evolution/tasks/:taskID/trace`

回傳指定任務最近的原始追蹤事件。追蹤事件是研究 UI 的旁路觀察資料，不是資料真源，不寫入 Postgres，不參與回測或進化決策。服務重啟後記憶體追蹤可消失，但 `EvolutionTask` 與 `GeneRecord` 仍以資料庫為準。

Trace mode 分為：

| 模式 | 說明 |
|---|---|
| `off` | 不產生原始追蹤 |
| `summary` | 任務、世代與整體生命週期事件 |
| `detailed` | 加入個體、窗口、交叉與變異事件 |
| `full` | 加入每根 bar 的策略步驟診斷，可能拖慢優化 |

### `PATCH /api/v1/evolution/tasks/:taskID/trace-mode`

切換任務原始追蹤模式。此操作只影響追蹤事件產生量，不改變資料載入方式、族群初始化、評估順序、選擇、交叉、變異或結果交付。

### `POST /api/v1/evolution/tasks/:taskID/cancel`

取消目前運行中的進化任務。取消必須透過 context 傳遞到 GA 與回測 adapter。任務取消後不得產生 challenger。

### 規劃但未實作

WFO 推進式滾動測試、定時自動觸發 GA、Nested Replay、前綴和滑窗統計與 Monte Carlo 非同步化都屬於規劃項目，不進入當前最小可用範圍。

### 8.1 參數誕生紀錄與分佈圖

參數搜尋可在 SaaS 層保存每一代評估完成後出現過的基因紀錄，包含 scope、搜尋設定雜湊、任務 ID、世代、個體序號、fingerprint、參數包、評分、最大回撤與 fatal 狀態。此紀錄是研究觀察資料，不改變適應度計算，不進入策略核心，也不得在策略核心加入 I/O。

參數搜尋設定頁可依目前選擇的標的、週期、資料區間、資料來源與執行假設查詢既有誕生紀錄，並顯示：

1. 平行座標圖：呈現核心參數各欄位分佈。
2. 降維散點圖：將核心參數標準化後投影到 2D，呈現整體參數族群分佈。

任務運行中，分佈圖可輪詢最新誕生紀錄即時更新。跨任務重新搜尋時，引擎應盡量避免產生與同搜尋設定下既有 fingerprint 完全相同的新隨機/子代基因；精英種子可保留作為比較基線。
