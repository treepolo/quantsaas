# 預測與動態參數計算量監控開發指導

> 文件定位：新功能開發指導草案
>
> 狀態：已確認，開發中
>
> 適用頁面：`預測與動態參數`
>
> 本文件不取代三份穩定系統真源文件，也不修改預測公式、模型驗證規則、動態政策或回測語義。

## 一、目的

讓「預測與動態參數」頁面的每個大量計算階段，都具備與參數搜尋相同的計算量監控能力：

- 執行前可預覽本階段計算量。
- 使用者可選擇是否開啟詳細計算量監控。
- 執行中可看到計算量持續增加。
- 顯示本次執行已計算量、預估剩餘量、計算速度與剩餘時間。
- 不因監控而為每一筆計算寫入資料庫。
- 計算中斷或重試時，不依賴計算量 counter 恢復正確性。

## 二、範圍

本階段納入兩個計算階段：

### 2.1 模型訓練階段

目前由兩個固定 manifest 項目組成：

```text
horizon-1：1 日模型
horizon-20：20 日模型
```

每個項目內仍會比較設定指定的回看天數，並分別訓練及驗證方向、上下行空間與路徑活動目標。

### 2.2 每日參數與回測階段

目前由一個固定 manifest 項目組成：

```text
materialize：每日預測、狀態、有效參數與回測
```

本階段內部會逐日處理資料，產生每日預測、結構狀態、每日有效核心參數、診斷資料及標準化回測結果。

### 2.3 不納入範圍

本文件不新增或修改：

- 預測目標定義。
- 預測模型公式。
- baseline gate 規則。
- 動態政策的參數邏輯。
- 固定參數與動態參數的回測語義。
- 策略核心的 I/O、資料庫或網路依賴。
- 交易、下單或實盤套用。

## 三、核心原則

### 3.1 兩種進度必須分開

任務同時有兩種進度：

```text
項目進度：已完成項目 / 總項目
計算量進度：本次已計算量 / 本次新增預估計算量
```

項目進度回答「哪個大項目完成了」。

計算量進度回答「目前實際做了多少工作，還剩多少工作」。

兩者不得互相取代。

### 3.2 詳細監控是可選功能，預設開啟

頁面增加「計算量監控」開關，預設必須為開啟。

- 預設開啟時：直接啟用估算工作量、實際計算量、計算速度與剩餘時間 counter。
- 使用者手動關閉時：仍保留通用任務的項目進度、狀態、錯誤、快取、取消與重試。
- 任務建立後，監控開關寫入不可變任務設定，不可在任務執行中切換。

### 3.3 counter 只服務本次執行

詳細計算量的語義固定為：

> 本次執行嘗試期間，已由 Executor 實際處理的估算工作單位。

它不是歷史累計量，也不是結果正確性的必要資料。

任務重試或重新執行時，counter 可以從本次執行重新開始；已完成結果仍由既有任務項目與計算快取管理。

### 3.4 不保存計算量 snapshot

計算量 counter 不做低頻率資料庫 snapshot。

禁止：

- 每個計算單位寫一次資料庫。
- 每次 counter 增加都更新任務資料列。
- 為了保存監控數字建立逐筆計算紀錄。

資料庫只保存原本就需要保存的：

- 任務狀態。
- 任務項目狀態。
- 項目進度與 checkpoint。
- 快取結果。
- 最終模型、預測、每日診斷與回測結果。

服務重啟後，計算量 counter 不需要恢復；新的執行嘗試重新計算即可，不影響結果正確性。

## 四、執行前計畫

所有大量階段都必須先產生固定計畫，再由使用者明確啟動。

### 4.1 模型訓練預覽

「預覽計算」必須展示：

- 本階段名稱。
- 總項目數。
- 每個項目的名稱與預估工作量。
- 可重用快取數。
- 實際新增項目數。
- 本次新增工作量估算。
- 是否超過建議上限。
- 是否超過硬上限。
- manifest hash。
- plan key。

訓練階段的項目固定為 1 日與 20 日，不因回看天數增加 manifest 項目數；回看天數屬於項目內部計算量。

### 4.2 每日參數與回測預覽

建立第二階段前，必須先預覽第二階段計畫，不得按下建立後才直接建立並開始大量計算。

預覽必須展示：

- 本階段名稱。
- `materialize` 項目。
- 預計處理的每日資料量。
- 預計產生的預測與有效參數處理量。
- 預計回測處理量。
- 可重用快取數。
- 實際新增項目數。
- 本次新增工作量估算。
- manifest hash。
- plan key。
- 軟上限與硬上限。

第二階段的計畫必須綁定第一階段產出的模型、預測 snapshot、政策 artifact、資料集 hash 與回測設定 hash。

### 4.3 計畫固定與防止暗中擴張

預覽完成後形成固定 manifest。

啟動後：

- 不得自動增加回看天數。
- 不得自動增加日期範圍。
- 不得自動增加驗證 fold。
- 不得自動新增回測項目。
- 不得因結果不理想而無限重跑。

若使用者修改設定，必須形成新的 plan key 與新的 manifest，並重新預覽。

## 五、計算量單位

### 5.1 定義

計算量單位是 Executor 使用的邏輯工作單位，不宣稱等於 CPU 指令數，也不直接等於秒數。

預估量與實際 counter 必須使用同一套工作邊界，才能使畫面上的比例有意義。

### 5.2 模型訓練階段

模型訓練階段至少涵蓋：

- 每個回看天數候選的特徵建立。
- 每個 fold 的訓練資料處理。
- 每個 fold 的驗證資料預測。
- 每個 epoch 的訓練樣本更新。
- 最終模型訓練。
- OOF 預測物化。

模型路線與目標模型內部若有不同的有限工作單位，必須在對應 Executor 內以同一版本的 unit contract 計數。

估算值必須根據固定設定與資料量形成，至少受到以下因素影響：

- 1 日或 20 日 horizon。
- 回看天數數量。
- 訓練資料筆數。
- fold 數。
- 最低訓練資料量。
- 模型路線。
- 訓練 epoch。
- 預測目標數量。

若某部分無法可靠估算，必須回報未知工作量，不得填入看似精確的假數字。

### 5.3 每日參數與回測階段

每日參數與回測階段至少涵蓋：

- 每日預測產生。
- 結構狀態更新。
- 動態政策套用。
- 每日有效參數產生。
- 每日診斷資料形成。
- 共用回測逐日推進。

計數必須在實際有限工作單位完成後累加，不得只在 Executor 開始與結束時回報兩個進度點。

### 5.4 預估量與快取

快取命中的項目不屬於本次新增計算量。

介面應分開顯示：

```text
計畫總工作量：所有 manifest 項目的估算量
本次新增工作量：扣除快取命中後真正需要執行的估算量
本次已計算量：本次執行 counter
```

詳細進度的分母以「本次新增工作量」為主；若全部命中快取，任務直接完成，不啟動 Executor。

## 六、執行中監控

### 6.1 記憶體 counter

Executor 取得與參數搜尋同語義的輕量 counter callback：

```text
CountUnits(delta)
```

開啟監控時：

- counter 使用 thread-safe 的記憶體累加器。
- 每個有限工作單位完成後增加 delta。
- 不在 callback 內執行資料庫寫入。
- 不在 callback 內建立結果資料列。

關閉監控時，callback 為空操作，不掛載詳細 counter。

### 6.2 API 即時回應

前端沿用參數搜尋的輪詢模式，在任務執行期間定期取得即時任務狀態。

API 回應可包含：

- `compute_monitor_enabled`。
- `computed_units`。
- `planned_compute_units`。
- `units_per_sec`。
- `remaining_seconds`。
- `compute_started_at`。
- `compute_updated_at`。

這些詳細欄位由服務內目前執行中的記憶體 counter overlay 產生，不要求先寫入資料庫。

### 6.3 顯示語義

畫面必須使用「本次執行」字樣，避免被誤解為歷史累計量：

```text
本次已計算：45,000 / 120,000
計算速度：2,100 單位／秒
預估剩餘：36 秒
```

若尚未取得有效速度，顯示「預估剩餘：未知」。

若實際計算量超過預估量：

- 不停止任務。
- 顯示已超過原始估算。
- 重新依目前速度估算剩餘量。
- 不修改原始 manifest 或 plan key。

### 6.4 計算速度與剩餘時間

基本計算方式：

```text
計算速度 = 本次已計算量 / 本次執行經過秒數
剩餘時間 = max(0, 本次新增預估量 - 本次已計算量) / 計算速度
```

若預估量未知、計算速度為零或預估量不可靠，剩餘時間顯示未知。

預估耗時是工作量估計，不是回測結果，也不是服務保證的完成時間。

## 七、資料庫、快取與重試

### 7.1 資料庫寫入規則

詳細計算量 counter 不寫資料庫。

既有通用任務的低頻進度與 lease 更新仍依通用計算任務框架執行，但不得把 `CountUnits` 接到既有的高頻 `Report` 寫入路徑。

### 7.2 結果正確性不依賴 counter

counter 遺失、歸零或服務重啟不應影響：

- 模型結果。
- 預測 snapshot。
- 動態政策。
- 每日有效參數。
- 回測結果。
- 快取驗證。

### 7.3 中斷與重試

使用者取消或 Executor 失敗後：

- 已完成的 task item 與快取結果保留。
- 未完成項目維持未完成、失敗或取消狀態。
- 任務不得標記為完整完成。
- 重試只處理未完成且沒有有效快取的項目。
- 詳細 counter 以新的執行嘗試重新計算。

重試畫面必須明確區分：

```text
已完成快取項目：可沿用
本次重新執行計算量：從零開始統計
```

### 7.4 計算快取

計算快取 key 必須涵蓋所有會改變結果的設定，包括：

- 資料內容 hash。
- 標的與資料來源。
- 週期與日期範圍。
- 模型路線。
- 回看天數。
- fold 與最低訓練資料量。
- 模型與預測 schema 版本。
- 基準參數與政策 hash。
- 回測執行時點與回測設定。

監控是否開啟不得改變計算結果的 cache key；它只改變是否掛載即時 counter。

## 八、取消與核心邊界

Executor 必須把 context 傳入長時間計算，並在以下邊界檢查取消：

- 回看天數候選。
- fold。
- epoch。
- 訓練樣本批次。
- OOF 預測批次。
- 每日資料處理。
- 回測逐日推進。

取消後不得讓整個模型或回測自然跑完才停止。

計算量 callback 位於 SaaS Executor 或回測 adapter 外層；策略核心與純量化核心不得新增資料庫、網路、檔案 I/O 或計時依賴。

## 九、前端操作流程

### 9.1 訓練階段

```text
填寫研究設定
  ↓
確認預設已開啟的計算量監控；如有需要才手動關閉
  ↓
預覽計算計畫
  ↓
查看總項目、快取、新增工作量、軟硬上限
  ↓
必要時確認超過建議上限
  ↓
建立訓練任務
  ↓
使用者明確按開始
  ↓
查看項目進度與即時計算量
```

### 9.2 每日參數與回測階段

```text
模型訓練完成
  ↓
建立每日參數與回測計畫預覽
  ↓
查看本階段計算量
  ↓
必要時確認超過建議上限
  ↓
建立第二階段任務
  ↓
使用者明確按開始
  ↓
查看逐日處理計算量
```

頁面不得因完成第一階段而自動啟動第二階段。

## 十、驗收條件

### 10.1 功能驗收

- 可以在訓練階段開啟或關閉詳細計算量監控。
- 可以在每日參數與回測階段開啟或關閉詳細計算量監控。
- 初次進入頁面與建立新階段時，詳細計算量監控預設為開啟。
- 訓練階段仍顯示 1 日與 20 日兩個項目。
- 每日參數與回測階段仍顯示固定 materialize 項目。
- 預覽計畫會顯示快取命中與本次新增工作量。
- 第二階段開始前必須先顯示第二階段計畫。
- 執行中計算量會持續增加，而不是只在項目完成時跳動。
- 執行中能看到速度與剩餘時間，無法估算時顯示未知。

### 10.2 資料庫驗收

- `CountUnits` 不會造成逐筆資料庫寫入。
- 計算量監控不會產生逐筆計算紀錄。
- 長時間執行期間，資料庫寫入量不會與計算單位數量成正比。
- counter 歸零或服務重啟不影響既有計算結果與快取。

### 10.3 取消與重試驗收

- 執行中取消可以在有限時間內停止。
- 已完成項目保留。
- 未完成項目可重試。
- 重試時 counter 以本次執行重新統計。
- 取消或部分完成不得標記為完整完成。

### 10.4 結果語義驗收

## 11. 後續修正：計算量動畫與即時活動狀態

本節納入本輪實作後確認的補充規格：

### 11.1 計算量統計不得膨脹

- `computed_units / planned_compute_units` 維持原本高層計算量單位。
- P09 訓練仍以「資料筆數 × lookback 候選數」為基本單位；TCN 僅保留既有路線權重。
- 不得把 epoch、fold、learner 更新次數直接乘入任務總量。
- 即時回報只能重新分配既有單位的回報時間，不能增加任務總量、上限判定或資料庫保存量。

### 11.2 即時活動狀態與計算量分離

```text
計算量累計：維持原本高層單位，不膨脹
即時活動狀態：固定間隔更新最後心跳與目前階段
```

- 執行器透過記憶體內 monitor 回報目前階段與最後心跳，不逐筆寫入資料庫。
- lease heartbeat 同步更新最後心跳，即使計算量尚未增加也能辨識工作仍在執行。
- 訓練階段至少回報目前 target 與 fold；物化階段回報每日診斷進度。
- fold 僅是階段標記，不是計算量唯一累加點；計算量應在驗證樣本處理過程中逐步分配既有候選預算，候選結束時補齊差額。
- learner 的每次訓練樣本更新也必須觸發計算事件；GAM／TCN 的低層事件由固定預算分配器映射為高層單位，不能直接把低層事件數當成任務總量。
- 分配器以目前 target 的既有候選預算為上限，按實際 learner 更新與驗證事件逐步釋放單位；若實際事件數與估算不同，候選結束時只補足尚未回報的差額。
- 分配器必須保證單一候選不超過其原有預算，整個任務完成時不超過 `planned_compute_units`；因此增加更新頻率不會改變計算量統計方式或任務上限判定。
- API 提供 `compute_current_stage` 與 `compute_last_heartbeat`；任務完成、失敗或取消後移除即時 monitor。

### 11.3 數字動畫

- `本次計算量` 的目前值到下一個值使用 1.2 秒補間動畫。
- 動畫只影響畫面呈現，不改變後端計數、估算量或任務結果。
- 進度條寬度同樣使用 1.2 秒 transition，與前端約 1.2 秒輪詢節奏銜接。

- 開啟或關閉監控不改變模型輸出。
- 開啟或關閉監控不改變回測結果。
- 相同資料、設定與版本仍使用相同結果快取。
- 不會因計算監控新增任何交易策略邏輯。

## 十一、開發前確認事項

使用者確認本文件前，不開始修改程式。

確認後才進入實作，實作順序應為：

1. 建立計算監控共用介面與即時 counter。
2. 將模型訓練 Executor 接上 counter。
3. 將每日參數與回測 Executor 接上 counter。
4. 增加兩階段預覽與監控 UI。
5. 補充取消、重試、快取與資料庫寫入量測試。
6. 使用固定入口執行格式化、測試與前端建置。

本文件確認前，任何「完成」回報都只能描述為設計完成，不得描述為功能已實作。
