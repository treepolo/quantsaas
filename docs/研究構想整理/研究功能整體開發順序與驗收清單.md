# 研究功能整體開發順序與驗收清單

> 狀態：P00、P01、P02、P03、P04、P05、P06、P07、P08 已完成；下一步為 P09
>
> 用途：統一管理本輪研究功能的跨模組依賴、實作順序、部分完成邊界、驗收關卡與舊系統退場時機。
>
> 文件定位：本文件不是三份穩定真源，不改寫各功能的公式、資料契約或完成判準。各功能「要做什麼」以個別開發指導文件為準；本文件只決定「依什麼順序做、何時可稱為完成」。

## 一、編排目標

本輪開發順序必須同時滿足：

1. 每日持倉、回測、結果保存、報酬分析與大量計算只建立一套共用底層。
2. 一次處理一個可驗收範圍，避免多個大型功能同時改動同一批核心程式。
3. 先鎖定回測與資料語義，再建立所有依賴它們的研究工具。
4. H、K、L、C 與 M 的交叉整合必須明確收口，不得把只有單邊連結的狀態稱為完成。
5. 舊參數搜尋與既有資料在 M 完整驗收前保持可用、可回復。
6. 每一步都具有進入條件、範圍、禁止事項、測試及退出條件。
7. 不以資料表、空 API、空頁面、單一圖表、假 payload 或只跑通 happy path 代表功能完成。

## 二、權責與衝突處理

### 2.1 文件權責

- 三份穩定真源：定義目前已穩定運作的系統。
- 各功能開發指導：定義該功能的完成品行為、公式、資料、API、UI、測試與完成判準。
- 本文件：定義跨功能開發順序、整合關卡與狀態。
- 討論稿與初步分組：保存決策脈絡，不直接作為實作規格或開發順序。

若本文件與個別開發指導的功能行為衝突，以個別開發指導為準；若是跨模組先後或何時可宣稱完成，以本文件為準。發現實際依賴不同時，必須先同步修正相關文件，不得直接在程式裡臨場改規格。

### 2.2 狀態名稱

固定使用：

- `未開始`：尚未進入該範圍。
- `進行中`：正在實作及驗證。
- `部分完成`：完成可用片段，但仍缺本文件明列的整合或完整驗收。
- `已完成`：個別開發指導的完整範圍、整合、測試與退出條件全部通過。
- `暫停待討論`：文件衝突、數學語義或產品決策不足，不能安全繼續。
- `阻擋`：依賴、資料或環境問題使本階段不能前進。

開發步驟編號完成，不等於其所屬字母大點必然完成。例如 P06 完成 E 的獨立核心後，E 仍是 `部分完成`，直到 P13 完成 E 與 L 的雙向來源限制及回歸測試。

### 2.3 不是 MVP

本文件採用依賴導向的分段實作，但不把任何分段包裝成 MVP。部分完成只表示最終架構中的一部分已落地，不代表可以省略後續範圍，也不得對外回報整個字母大點已完成。

## 三、不形成獨立開發步驟的字母大點

- A 是整套研究能力共同支撐的抗過擬合與樣本外驗證目標，不新增獨立頁面、模組、評分或資料表。
- B 由既有跨商品回測，以及 E 產生同週期跨商品行情後交由 M 研究共同參數來滿足，不新增獨立模組。
- F 已取消，不建立蒙地卡羅或 bootstrap 功能。

因此本文件不為 A、B、F 安排獨立程式階段。

```text

  → 共用回測核心
    → 標準化回測結果
      → G 報酬分析
        → I 計算任務與快取

I
  → E K 線片段重組核心 ───────────────┐
  → D 長週期濾網 → J 穩健區域分析      │
  → K 預測／狀態／動態政策核心           │
                                           ↓
J + K 核心 → M 主要研究系統與候選連結
                  → H 對照系統整合
                  → C K 線反推整合
                  → L 擾動行情整合 ← E 核心
                                    → 關閉 E/L 循環依賴

H + C + L + K 完整整合
  → M 完整驗收與舊搜尋退場
    → N 唯讀比較工具
      → 全系統驗收與穩定真源同步
```

補充：

- E 與 L 的核心沒有單向硬依賴，但兩者的完成品都要求雙向來源限制測試，因此以 P13 統一收口。
- K 的模型、預測、狀態與政策可先完成；K 的完整參數研究需接入 M，完整採用單位還需能交給 L 重跑。
- M 可先建立研究、候選及連結真源；M 只有在 H、L、C、K 全部接入後才能完成。
- N 只讀已保存成果，不依賴 I，也不得補算任何來源。

## 二十四、每個程式階段的固定工作流程

### 24.1 開工前

每一階段開始前，Agent 必須回報：

- 本階段對應文件。
- 一次到位範圍。
- 本階段明確不處理的內容。
- 進入條件是否成立。
- 預計修改的模組與資料表。
- 測試矩陣。
- 完成定義與已知風險。

若規格不足，先補文件並取得確認，不得直接猜量化邏輯。

### 24.2 實作順序

單一階段內預設依序：

1. 建立或補齊 characterization／失敗測試。
2. 實作純數學或 domain 核心。
3. 實作 GORM model、repository 與服務生命週期。
4. 實作 API 與權限、輸入驗證、錯誤分類。
5. 實作前端完成品、空白／載入／部分完成／失敗／封存狀態。
6. 執行針對性測試。
7. 執行完整 Go 測試及前端 build。
8. 以實際瀏覽器完成桌面與行動版主要流程驗收。
9. 若有資料或退場操作，完成備份還原及回退演練。
10. 依退出條件逐項核對後才更新狀態。

### 24.3 固定工具入口

- Go 格式化：`scripts/dev/go-fmt.ps1`
- Go 測試：`scripts/dev/go-test.ps1`
- 前端建置：`scripts/dev/frontend-build.ps1`
- Docker 操作：`scripts/dev/compose-*.ps1`
- 日常重啟：`重啟軟體.bat`
- 只有程式碼或容器建置內容改動才重新建置，不因一般重啟濫用 build。

### 24.4 收工

每一階段收工必須回報：

- 狀態：已完成／部分完成／未完成／暫停待討論。
- 完成與未完成清單。
- 實際測試及結果。
- 資料／API／UI 相容性。
- 已知風險與回退方式。

程式階段完成後，依使用者要求提交、推送並重啟服務；重啟後必須檢查服務狀態與主要頁面。純文件階段不因沒有執行碼變更而重啟服務。

## 二十五、共通測試最低要求

每個相關階段按風險涵蓋：

- 純函數與數學不變量測試。
- canonical JSON、hash、map 順序與版本穩定性。
- 回測逐日路徑與基線回歸。
- GORM／Postgres repository、唯一鍵、交易與併發測試。
- AutoMigrate 啟動及既有資料相容測試；不建立 SQL migration。
- API 權限、非法輸入、版本衝突、缺失與損壞測試。
- I 的進度、取消、部分完成、失敗、重試、重啟及快取測試。
- 前端載入、空白、部分完成、失敗、封存、長文字與響應式測試。
- 圖表非空、資料一致、隱藏分頁停止渲染及低功耗測試。
- 備份、還原、舊版本引用及資料退場測試。
- 不含交易所憑證、私鑰或其他秘密的 fixture 與日誌檢查。
