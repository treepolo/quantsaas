# 研究功能後續開發指導

**文件目的：** 本文件整理使用者已確認的後續研究功能方向，供下一輪中等思考強度實作時依序執行。這是一份開發指導與驗收清單，不取代三份真源文件。開始寫程式前，若本文件內容尚未出現在 `docs/系統總體拓撲結構.md`、`docs/策略數學引擎.md`、`docs/進化計算引擎.md`，必須先同步或補入對應真源文件，再改程式。

---

## 0. 總原則

1. 目前仍暫停交易功能，不新增下單、執行端、交易 API、券商串接或資金操作。
2. 後續重點是研究：資料匯入、自動更新、參數搜尋、回測、候選參數管理與市場狀態判讀。
3. 不接 Shioaji 作為第一階段資料源。Shioaji 只保留給未來台股即時資料或交易需求。
4. 第一階段改用 Yahoo Finance 類資料源做多標的日 K 研究；BTC 日 K 維持 Binance 公開行情資料。
5. 非 BTC 研究標的只做日 K，不做 1m、5m、15m、1h 等日內回測或參數搜尋。
6. 不為了畫面炫或資料完整而改變策略核心、資料載入或 GA 生命週期。新增觀察、取消、範圍選擇都必須是外圈能力。
7. 交易所或資料商憑證不得進入資料庫、前端、測試 fixture 或日誌。Yahoo Finance 目前不需要憑證；若未來接商業資料商，憑證只能進本機或服務端設定，不可入庫。

### 0.1 已確認的後續調整

1. 研究商品清單改為可由使用者新增、停用與排序；所有頁面必須共用同一份啟用商品清單與排序。
2. 非 BTC 商品也可依商品支援週期匯入 `1m`、`1h`、`1d`、`1w`、`1M` 等資料，並可用於參數搜尋與回測；可用週期由商品設定控制，不再以前端硬限制日 K。
3. 自動更新需跑各商品的所有支援週期，包含週 K；資料頁要能一眼看出各市場、各商品、各週期是否更新至理論最新資料。
4. 回測頁的本金、月投入與定投基準投入必須由本次回測設定統一指定，避免不同參數包內的出生點資金造成多參數比較不公平。
5. 回測結果必須同時顯示策略與定投基準的總報酬、最大回撤、期末權益。
6. 回測頁與市場狀態頁圖表使用單一時間範圍滑塊：拖左邊界改起點，拖右邊界改終點，拖滑塊本體平移區間；不再使用圖表滾輪縮放或圖表拖曳平移。
7. 圖表游標讀值需同步顯示日期、該日價位或點數、淨值、日變化、目標權重與權重變化。
8. 市場狀態頁需可切換同一商品的日 K 參數與週 K 參數判讀；若缺少該週期資料或已採用參數，需明確顯示缺漏狀態。

## 1. 研究標的範圍

第一階段只支援以下標的：

| 研究標的 | instrument_id | 資料源 | 週期 |
|---|---|---|---|
| 台灣加權指數 | `^TWII` | Yahoo Finance provider | `1d` only |
| S&P 500 | `^GSPC` | Yahoo Finance provider | `1d` only |
| Nasdaq 100 | `^NDX` | Yahoo Finance provider | `1d` only |
| 費城半導體指數 | `^SOX` | Yahoo Finance provider | `1d` only |
| SOXL | `SOXL` | Yahoo Finance provider | `1d` only |
| Bitcoin 現貨 | `BTCUSDT` | Binance Spot public API | `1d` 優先，既有其他週期保留但非多標的重點 |

不得做成任意 symbol 全市場匯入器。UI 下拉選單只列出上述 6 個標的。

只要 UI 有多商品可選清單，顯示順序固定為：台灣加權指數、標普 500、納斯達克 100、費城半導體、SOXL、比特幣。

Yahoo Finance / `yfinance` 適合個人研究，但不是商業級授權資料來源。程式架構必須有 provider interface，避免未來商業化時被 Yahoo 寫死。

## 2. 多標的資料與參數隔離

目前 BTC 參數與未來指數/ETF 參數不得混在一起。所有研究資料、任務與參數都必須至少以以下維度隔離：

```text
strategy_id
instrument_id
interval
data_source
execution_mode
```

建議欄位語義：

| 欄位 | 說明 |
|---|---|
| `strategy_id` | 策略模板，例如目前的 sigmoid DCA |
| `instrument_id` | `BTCUSDT`、`^TWII`、`^GSPC` 等 |
| `interval` | 第一階段多標的只允許 `1d` |
| `data_source` | `binance`、`yahoo` |
| `execution_mode` | 研究執行假設，見第 4 章 |

`champion` 唯一性必須依上述組合判斷，而不是全策略只允許一個 champion。也就是 BTC 的已採用參數不能覆蓋加權指數，加權指數也不能覆蓋 SOXL。

## 3. 自動日 K 更新

### 3.1 BTC 日 K

BTC 日 K 使用 Binance public API。建議每日台灣時間 08:05 之後更新，因 Binance 日線以 UTC 切日，台灣時間早上 08:00 才完成前一日 K 線。

### 3.2 Yahoo 標的日 K

Yahoo 標的使用 Yahoo Finance provider 更新日 K。

建議排程：

| 市場 | 標的 | 建議更新時間 |
|---|---|---|
| 台股 | `^TWII` | 台灣時間 15:00 後 |
| 美股 | `^GSPC`、`^NDX`、`^SOX`、`SOXL` | 台灣時間每日早上，避開美股收盤資料延遲 |

保留手動匯入按鈕。自動更新失敗時應在資料狀態頁顯示最後成功時間與錯誤訊息，不應讓整個服務失敗。

### 3.3 不做資料推送假設

Yahoo/Binance 皆以排程抓取為主，不假設資料源會主動推送最新日 K。

## 4. 研究執行假設

日 K 的訊號時間與可執行時間必須明確建模，不能偷偷用不可執行的假設高估結果。

第一階段支援三種 `execution_mode`：

| execution_mode | 說明 | 用途 |
|---|---|---|
| `close_same_bar` | 使用當日 close 產生訊號，假設同一根日 K close 可調倉 | 理論基準，可能不可執行 |
| `close_next_open` | 使用當日 close 產生訊號，以下一交易日 open 作為執行價 | 保守且較可執行，但承擔跳空 |
| `preclose_10m` | 使用收盤前 10 分鐘快照產生訊號，假設接近收盤前調倉 | 貼近人工盤中操作，但需要日內快照資料 |

參數搜尋、回測、市場狀態頁必須使用同一個 `execution_mode`。不得用 `close_same_bar` 搜尋，再用 `close_next_open` 宣稱同一組參數可執行。

第一版不要把三種模式混成同一個適應度函數。較佳流程是：

```text
選一種 execution_mode 做參數搜尋
完成後用其他 execution_mode 做交叉回測
比較該參數是否只適合單一假設
```

### 4.1 preclose_10m 的資料限制

`preclose_10m` 不應把完整日內資料拿去 GA 長期跑。應新增「每日執行快照」概念：

```text
daily_execution_snapshots
date
instrument_id
mode = preclose_10m
price
timestamp
source
```

若資料源只能提供近期日內資料，歷史 `preclose_10m` 回測與參數搜尋只能使用已蒐集到的快照區間。不能用不存在的歷史快照假裝回測。

## 5. 優化實驗室改造

### 5.1 標的選擇

建立優化任務時新增：

```text
instrument_id
data_source
interval
execution_mode
```

UI 對非 BTC 標的只允許 `1d`。

### 5.2 資料時間範圍

建立優化任務時新增：

```text
train_start
train_end
```

範圍限制要作用於 GA 的資料載入與窗口建構。若資料不足以構造評估窗口，API 要回傳清楚錯誤。

這是為了：

1. 避免 1m 或長歷史資料任務算到無法完成。
2. 允許使用者排除過舊市場結構。
3. 讓參數搜尋結果更貼近指定研究區間。

UI 名稱建議使用「參數搜尋」或「進化最佳化」，不要把主要功能稱為「資料探勘」。資料探勘可作口語描述，但產品 UI 應更精準。

### 5.3 任務取消

新增「中止任務」按鈕。

後端要求：

1. `epoch.Service` 必須持有可取消的 `context.Context`。
2. GA loop、個體評估、窗口評估、回測 adapter 必須定期檢查 `ctx.Err()`。
3. 中止後任務狀態為 `cancelled`。
4. trace viewer 顯示任務中止事件。
5. 中止任務不得產生 `challenger`。

## 6. 參數庫可逆性

目前 Promote 不可逆，後續要改為可回復、可審核的研究流程。

需求：

1. `candidate`、`champion`、`retired` 都能回測。
2. `candidate` 可設為已採用參數。
3. `retired` 可重新設為已採用參數。
4. 未採用的 `candidate` 可刪除或封存。
5. 每個 `strategy_id + instrument_id + interval + execution_mode` 組合只能有一個 active champion。
6. Promote/restore 必須在資料庫交易內完成。

UI 名稱：

| 內部角色 | 使用者可見名稱 |
|---|---|
| `challenger` / `candidate` | 候選參數 |
| `champion` | 已採用參數 |
| `retired` | 歷史參數 |

## 7. 市場狀態判讀頁

新增一頁「市場狀態」或「狀態判讀」，一次只顯示 1 個研究標的在已採用參數下的目前判斷。使用者可切換標的，並可設定其中一個標的作為市場狀態頁首頁預設。

每個標的卡片至少顯示：

1. 標的名稱與資料源。
2. 最新資料日期與資料是否過期。
3. 目前使用的 `execution_mode`。
4. 已採用參數版本與建立時間。
5. 核心參數表。
6. 策略 diagnostics。
7. 市場狀態。
8. Sigmoid 目標浮動倉位。
9. 目前浮動倉位與目標差距若無實際持倉資料，顯示為研究估算，不假裝有真實倉位。

市場狀態主區應以「基準模型」為正式模型輸出。基準模型設定與回測的基準模型一致：從指定起點空倉與本金開始，逐日呼叫 `Step()` 並依模型輸出調整持倉。市場狀態頁的基準模型起點不可由使用者任意改日期；本金與定期入金金額可沿用倉位模擬系統的設定。原倉位模擬系統仍保留，但移到下方可收合區塊，預設收合。

市場狀態頁圖表至少包含：

1. 基準模型淨值走勢。
2. 空倉參考目標權重每日值。
3. 空倉參考目標權重每日變化值。
4. 基準模型目標權重每日值。
5. 基準模型目標權重每日變化值。

所有圖表的縮放、拖曳、游標豎線、tooltip 與底部滑塊操作需比照回測頁。

### 7.1 核心參數顯示方式

不要讓前端硬寫特定染色體欄位。後端應回傳泛用 schema/value：

```json
{
  "schema": [
    {"key": "beta", "label": "Beta", "description": "..."}
  ],
  "values": {
    "beta": 2.0
  }
}
```

前端只依 schema/value 渲染表格。這樣可以顯示數學欄位，又不讓 UI 綁死策略內部實作。

### 7.2 PVA / SJM 注意事項

目前三份真源文件沒有定義 `SJM`，也沒有正式定義 P/V/A 三特徵作為策略輸入。因此第一版不得憑影片印象硬實作 `SJM`。

第一版狀態判讀頁應使用目前策略已存在的 diagnostics，例如：

```text
signal
current_weight
target_weight
delta_weight
volatility_ratio
market_beta
market_trend_slope
market_drawdown
```

若未來要做 PVA 或三態感知，必須先補 `docs/策略數學引擎.md`，明確定義：

1. P/V/A 的公式。
2. 使用哪些價格序列。
3. 是否取代或並存於現有市場狀態感知層。
4. 三態名稱與判斷方式。
5. 是否進入染色體與適應度函數。

## 8. 回測調整

回測必須支援：

1. `instrument_id`
2. `interval`
3. `data_source`
4. `execution_mode`
5. `start_date`
6. `end_date`
7. 指定候選參數、已採用參數、歷史參數

回測結果要清楚顯示使用的執行假設，避免 `close_same_bar` 與 `close_next_open` 混淆。

對 `close_next_open`，策略訊號由第 N 根日 K 產生，交易效果反映在第 N+1 根 open。不得在同一根 bar 使用 close 訊號又用 close 成交。

回測頁圖表需新增：

1. 基準模型目標權重每日值。
2. 基準模型目標權重每日變化值。
3. 空倉參考目標權重每日值。
4. 空倉參考目標權重每日變化值。

基準模型為回測策略路徑本身：從回測起點空倉開始，當模型產生目標水準時即依模型目標水準持倉。空倉參考則是每天獨立假設昨日為空倉，計算該日參考目標權重。圖表橫軸範圍、滑塊、游標豎線與 tooltip 必須同步。

## 9. 資料模型建議

不建立 SQL migration；只改 GORM model 並由 AutoMigrate 管理。

建議新增或擴充：

```text
ResearchInstrument
KLine
DailyExecutionSnapshot
EvolutionTask
GeneRecord
BacktestRun
```

必要索引：

```text
KLine: source + symbol/instrument_id + interval + open_time unique
DailyExecutionSnapshot: source + instrument_id + mode + trade_date unique
GeneRecord: strategy_id + instrument_id + interval + execution_mode + role
EvolutionTask: strategy_id + instrument_id + interval + execution_mode + status
BacktestRun: strategy_id + instrument_id + interval + execution_mode + source
```

若現有 `KLine` 使用 `symbol`，可以先延伸為 `instrument_id` 概念，但要避免大規模破壞現有 BTC 流程。

## 11. 開發順序

### Phase 0：同步真源文件

把本文件被採用的規格同步到三份真源文件中。尤其是：

1. 多標的研究邊界。
2. Yahoo provider 與商業化 caveat。
3. execution_mode。
4. 任務取消。
5. 參數庫可逆狀態。
6. 市場狀態判讀頁。

### Phase 1：資料源與標的

1. 建立研究標的清單。
2. 建立 provider interface。
3. 接 Yahoo daily provider。
4. 保留 Binance BTC daily provider。
5. 資料狀態頁顯示 6 個標的覆蓋範圍。
6. 自動日 K 更新。

### Phase 2：多標的隔離

1. 擴充 `EvolutionTask`、`GeneRecord`、`BacktestRun`。
2. 所有查詢依 `instrument_id + interval + execution_mode` 過濾。
3. Champion 不再全策略唯一，而是依研究標的組合唯一。

### Phase 3：優化實驗室

1. 任務表單加入標的、資料時間範圍、execution_mode。
2. 非 BTC 標的鎖定 `1d`。
3. 任務可取消。
4. trace viewer 中顯示取消事件。
5. 任務狀態增加 `cancelled`。

### Phase 4：回測

1. 回測支援標的、時間範圍、execution_mode。
2. 支援 candidate/champion/retired。
3. 明確顯示執行假設。
4. 支援交叉回測：同一參數可用其他 execution_mode 驗證。

### Phase 5：市場狀態判讀頁

1. 新增研究狀態頁。
2. 顯示 6 個標的。
3. 顯示已採用參數、核心參數表、diagnostics、目標浮動倉位。
4. 缺少 champion 時顯示「尚無已採用參數」，不得用 BTC 參數代替。

### Phase 6：preclose_10m

1. 新增 daily execution snapshot model。
2. 新增快照匯入/更新。
3. 回測與參數搜尋在資料足夠時才開放 `preclose_10m`。
4. UI 顯示資料覆蓋不足警告。

## 12. 驗收標準

每個 phase 至少驗證：

```powershell
go test ./...
npm run build
docker compose --project-name quantsaas up -d --build
```

功能驗收：

1. BTC 與 5 個 Yahoo 標的都能顯示日 K 覆蓋範圍。
2. 自動更新不需要手動輸入 API key。
3. 任務建立時能選標的、時間範圍與 execution_mode。
4. 運算中可取消，取消後不產生候選參數。
5. 參數庫可回測、可重新設為已採用、可刪除未採用候選。
6. 市場狀態頁不混用不同標的的已採用參數。
7. `close_same_bar`、`close_next_open`、`preclose_10m` 的結果不互相冒充。

## 13. 明確不做

1. 不在本階段接 Shioaji。
2. 不做交易功能。
3. 不做任意股票/指數全市場搜尋。
4. 不把 Yahoo Finance 當作商業級保證資料源。
5. 不在策略核心新增 I/O、網路、資料庫、時間或隨機依賴。
6. 不把 PVA/SJM 依影片印象硬寫進程式；需先有真源文件定義。
7. 不讓 `preclose_10m` 在缺乏歷史快照時假裝可長期回測。

1. 研究標的改由 SaaS DB 的 `ResearchInstrument` 管理，使用者可在研究資料頁手動新增或停用研究商品。所有行情資料、參數搜尋、回測、市場狀態與參數庫頁面必須共用同一份啟用標的清單。
2. 內建種子標的包含 `TQQQ`、`SQQQ`、`SOXL`、`SOXS`、`TWII`、`GSPC`、`NDX`、`SOX`、`BTCUSDT`。預設顯示排序為：TQQQ、SQQQ、SOXL、SOXS、台灣加權指、標普 500、納斯達克 100、費城半導體、比特幣。
3. Yahoo Finance 類 provider 的研究標的預設支援 `1d`、`1h`、`1m`、`1w`、`1M`；Binance Spot public provider 預設支援 `1d`、`1h`、`15m`、`5m`、`1m`、`1s`、`1w`、`1M`。前端可依標的設定顯示可用週期，後端必須以標的設定驗證匯入、參數搜尋與回測。
4. 自動更新以排程拉取為主，不假設資料源會主動推送。排程與手動「更新全部」必須掃描所有啟用標的與其支援週期，補齊缺少的最新資料。
5. 行情資料頁必須提供資料新鮮度總覽，按市場分組顯示每個啟用標的各週期是否更新到理論最新資料。第一筆與最後一筆資料時間必須顯示年份。
6. Yahoo Finance 仍只定位為個人研究資料來源，不作商業級授權資料保證；provider 介面必須保留未來替換正式資料商的空間。
