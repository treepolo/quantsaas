# 系統總體拓撲結構

**文件目標：** 定義 QuantSaaS 全域有哪些物理端、有哪些邏輯模組、狀態如何在它們之間流轉，以及系統整體生命週期。不含任何具體策略公式。

---

## 第 0 章：架構哲學

QuantSaaS 採用「時空正交」的設計：每一次業務推進都必須是一個離散動作，動作讀取當下快照，產出新的確定性意圖，不依賴上一個動作留在記憶體中的隱式狀態。這讓實盤、回測與進化都能被同一套快照模型驅動。

系統的核心不是追求單一交易訊號，而是讓資產狀態、策略決策、執行回報與參數進化分別存在於清楚的邊界內。策略只看它被允許看到的輸入，Agent 只做它被要求執行的命令，Lab 只做離線計算。

所有跨模組流轉都必須可追溯、可重放、可審計。任何需要「相信某個記憶體變數仍然正確」的流程，都不是合格流程。

---

## 第 1 章：三端物理部署形態

### SaaS 管理端（雲端，`app_role: saas`）

SaaS 是決策大腦，負責使用者、策略模板、策略實例、WebSocket Hub、cron tick、審計與資料真源管理。它會掃描 `RUNNING` 實例，在最新已完成聚合桶尚未處理時執行一次 `Step()`，再把策略意圖翻譯為交易命令。

SaaS 不持有交易所 API Key，也不直接接觸使用者的交易所密鑰。它只能透過 Agent 上報的成交與餘額快照修正自己的狀態。

在 `app_role: saas` 下，GA 進化與回測寫入型接口必須被路由層禁止，避免雲端正式服務變成算力實驗環境。

### LocalAgent 執行端（使用者本地）

LocalAgent 是極簡執行手，使用者在本地運行。它讀取 `config.agent.yaml`，保存 SaaS 連線資訊與交易所 API 憑證，登入 SaaS 取得 JWT 後建立 WebSocket 長連線。目前預設執行 adapter 為 Binance Spot；測試模式使用 Binance Spot Testnet。

Agent 收到 `TradeCommand` 後呼叫交易所 REST API 下單，取得成交明細與餘額後組成 `DeltaReport` 上報 SaaS。它不連資料庫，不自主決策，不包含任何策略程式碼。

Agent 斷線後以指數退避重連；重連成功後立即上報初始餘額快照，讓 SaaS 在下一次 tick 自動收斂狀態。

### Lab 進化算力面（本地實驗室，`app_role: lab`）

Lab 是完整 SaaS 系統的本地算力部署，連接同一個 Postgres，專門執行 GA 進化與回測。它可以讀取策略、K 線、基因庫與歷史資料，但不得下發真實交易命令。

Lab 用於產出 `challenger` 基因包，等待人工審核後才能晉升為 `champion`。這個分離保證參數探索不會直接污染實盤。

在 `app_role: lab` 下，實例啟停與交易下發路由必須禁止，防止實驗環境誤觸真實交易流程。

## 第 2 章：`app_role` 三態行為矩陣

| 角色 | 部署場景 | 開放能力 | 限制 |
|---|---|---|---|
| `saas` | 雲端正式服務 | 使用者管理、實例管理、策略 tick、交易命令下發、Agent 連線管理 | 禁止進化任務與回測寫接口 |
| `lab` | 本地算力實驗室 | GA 進化、回測、基因庫管理、策略研究 | 禁止交易命令下發，實例只讀或不可啟停 |
| `dev` | 開發測試 | 所有模組開放，允許端到端開發 | 不作生產安全假設 |

`app_role` 是運行時能力開關，不是程式碼分叉理由。相同 Go binary 可用不同設定啟動出不同角色，但策略、模型與資料契約保持一致。

所有具破壞性或資金相關能力都必須在路由層與 service 層雙重檢查 `app_role`，避免單點疏漏。

## 第 3 章：邏輯模組與職責邊界

### Strategy 策略模組

Strategy 模組管理策略模板、策略版本、交易標的能力、參數契約與唯一決策入口 `Step()`。策略內核只接受 `StrategyInput`，只輸出 `StrategyOutput`。

回測與實盤必須呼叫同一個 `Step()`，禁止在策略內部判斷目前是回測或實盤。現貨策略不得直接依賴 `quant.Bar`，OHLCV 降級需在外圈 adapter 完成。

Strategy 模組不讀資料庫、不呼叫網路、不碰交易所憑證，也不處理使用者認證或訂閱。

### Instance 實例模組

Instance 是策略模板、交易標的、資金配額、使用者授權與運行狀態的綁定體。它管理建立、啟動、停止、刪除，以及 `RUNNING` / `STOPPED` / `ERROR` 狀態。

cron tick 只對 `RUNNING` 實例工作，並以最新已完成聚合桶做冪等保護。同一根 bar 或同一聚合桶不得重複推進策略。

Instance 模組負責把 `StrategyOutput` 翻譯成 `TradeCommand`，並在資料庫寫入 pending 執行記錄。

### Evolution 進化模組

Evolution 模組是參數實驗室，透過抽象 `EvolvableStrategy` 介面驅動種群生命週期。它不認識具體策略染色體欄位，也不 import 具體策略內部實作。

進化任務產出的基因一律先以 `challenger` 寫入資料庫。人工 Promote 後才會成為 `champion`，並讓 Redis 冠軍快取失效。

Evolution 只能在 `lab` 或 `dev` 開放寫入型任務；`saas` 可查詢結果但不可啟動算力任務。

Evolution 的研究資料與參數必須依 `strategy_id + instrument_id + interval + data_source + execution_mode` 隔離。不同標的不得共用 champion；例如 `BTCUSDT` 的已採用參數不可套用到 `^TWII`，`^SOX` 的候選參數也不可污染 `SOXL`。

### Research 研究資料模組

Research 模組管理研究標的清單、資料供應商、日 K 覆蓋狀態、自動更新與市場狀態判讀。第一階段只支援下列研究標的：`^TWII`、`^GSPC`、`^NDX`、`^SOX`、`SOXL`、`BTCUSDT`。UI 中只要有多商品清單，顯示順序固定為台灣加權指、標普 500、納斯達克 100、費城半導體、SOXL、比特幣。除 BTC 既有資料外，非 BTC 標的只支援日 K。

市場狀態頁一次只顯示一個研究標的，可由使用者選擇目前標的，並可把任一標的設為市場狀態首頁預設。主要資訊區顯示最新完成日 K、已採用參數、基準模型目標權重、基準模型目標權重變化、空倉參考目標權重與空倉參考目標權重變化。倉位模擬系統保留，但移至下方可收合區塊，預設收合，避免與正式研究判讀混淆。

資料供應商必須透過 provider 介面接入。第一階段 BTC 日 K 由 Binance Spot public API 提供，其他研究標的由 Yahoo Finance 類 provider 提供。Yahoo Finance 類 provider 只作個人研究資料來源，不作商業級資料保證；未來可替換為正式授權資料商。

Research 模組不得儲存券商或資料商憑證。若未來接入需要憑證的商業資料源，憑證只能存在服務端設定或本機設定，不得進入 SaaS DB、前端、日誌或測試 fixture。

### Auth 認證模組

Auth 模組負責註冊、登入、JWT 簽發、JWT 驗證與訂閱方案守門。它不介入策略計算，也不讀取交易所憑證。

Agent 與 SaaS 的 WebSocket 連線必須先通過 JWT 鑑權。未鑑權連線需在短時間內關閉，避免長時間佔用資源。

使用者啟動實例或建立資金配置時，訂閱與配額檢查由 Auth 或訂閱 service 提供明確結果。

## 第 4 章：全域狀態總線

系統使用單一 Postgres 作為資料真源，資料庫名稱預設為 `quantsaas`。Redis 只做快取，例如 champion 基因快取、會話快取與短期計算結果，不作可靠事件匯流排，也不作交易訊號傳遞通道。

資料所有權必須清楚。誰產生資料、誰能修改資料、誰只能讀取資料，都要落到表與 service 邊界上。

| 資料類型 | 真源 | 說明 |
|---|---|---|
| 策略決策邏輯 | `Step()` 實作 | SaaS 側執行，回測與實盤共用 |
| 策略模板與 champion 基因 | SaaS DB | 進化產出與人工 Promote 後保存 |
| 使用者與訂閱 | SaaS DB | SaaS 統一管理 |
| 實例狀態 | SaaS DB | Agent 上報後更新 |
| 交易所 API 憑證 | LocalAgent `config.agent.yaml` | 永不進入 SaaS |
| 成交與資產快照 | SaaS DB | Agent 透過 `DeltaReport` 上報 |
| GA 任務與基因紀錄 | SaaS DB | 單一資料庫，不分庫 |
| 研究標的與日 K | SaaS DB | 研究資料真源，依 provider 與標的隔離 |
| 盤前/盤中研究快照 | SaaS DB | 僅供指定 execution mode 使用，不得冒充正式日 K |
| 快取資料 | Redis | 可重建，不可作唯一真源 |

## 第 5 章：WebSocket 通訊協議

Agent 主動連線 SaaS 的 `/ws/agent`。連線建立後必須先傳送 `auth` 訊息並攜帶 JWT，SaaS 驗證成功後回傳 `auth_result`，之後才進入正常命令與上報流程。

| 訊息類型 | 方向 | 觸發時機 |
|---|---|---|
| `auth` | Agent → SaaS | 連線建立後立即送出，攜帶 JWT |
| `auth_result` | SaaS → Agent | 鑑權完成後回傳 |
| `heartbeat` | Agent → SaaS | 每 30 秒 |
| `heartbeat_ack` | SaaS → Agent | 收到心跳後 |
| `command` | SaaS → Agent | `Step()` 產出交易意圖後下發 |
| `command_ack` | Agent → SaaS | 收到 command 後立即確認 |
| `delta_report` | Agent → SaaS | 交易完成後，或重連時上報初始餘額 |
| `report_ack` | SaaS → Agent | SaaS 成功處理回報後 |

### `TradeCommand` 欄位語義

| 欄位 | 語義 |
|---|---|
| `client_order_id` | 全域唯一命令 ID，格式如 `inst{id}-{engine}-{ts}`，用於冪等與審計 |
| `action` | `BUY` 或 `SELL` |
| `engine` | `MACRO` 或 `MICRO`，標示命令來源層 |
| `symbol` | 交易對，例如 `BTCUSDT` |
| `amount_usdt` | 買入時使用，代表花費 USDT 金額 |
| `qty_asset` | 賣出時使用，代表賣出標的數量 |
| `lot_type` | `DEAD_STACK` 或 `FLOATING`，標示倉位語義 |

### `DeltaReport` 欄位語義

`DeltaReport` 包含目前餘額快照、成交明細、對應的 `client_order_id`。重連後的初始快照可不含成交明細，但必須足以修正 SaaS 側 `PortfolioState`。

SaaS 收到回報後刷新資產快照、寫入成交明細、寫審計日誌並確認 pending 執行紀錄。下一次 `Step()` 以真實餘額重新決策，因此 Agent 斷線與重連可自然收斂。

## 第 6 章：系統級生命週期動作

### 系統初始化

SaaS 啟動時讀取 `config.yaml`，初始化 DB、Redis、JWT、logger 與 HTTP router。接著執行 GORM AutoMigrate，以 Go struct 同步資料表結構。

初始化完成後，SaaS 讀取目前 `RUNNING` 實例，啟動 WebSocket Hub，註冊 cron 掃描任務，等待 Agent 連線。

所有啟動錯誤都必須清楚記錄，不得在缺少 DB 或 JWT secret 時靜默降級啟動。

### Cron Tick 驅動 `Step()`

cron 掃描 `RUNNING` 實例後，先確認該實例最新已完成聚合桶尚未處理。若已處理，直接跳過以保證冪等。

tick 流程依序讀公開 K 線、讀 `PortfolioState`、讀 `RuntimeState`、組成 `StrategyInput`、呼叫 `Step()`、翻譯 `StrategyOutput`、寫 pending 執行紀錄、透過 WebSocket 下發命令。

若 Agent 未連線，SaaS 不嘗試自己交易，只記錄警告並等待下一次 tick。

### Agent 斷線重連

Agent 偵測 WebSocket 中斷後，從 1 秒開始做指數退避，最大等待 5 分鐘。每次重連都重新登入取得 JWT，再建立新的 WebSocket。

重連成功後，Agent 立即送出不含成交的初始 `DeltaReport`，讓 SaaS 更新真實餘額。下一次 tick 會以新快照決策。

這個流程不需要人工補單，也不需要 Agent 記憶之前 SaaS 的策略狀態。

### 優雅停機與狀態快照

SaaS 收到中斷信號後停止接受新 Agent 連線與新 tick，等待已在執行中的 tick 完成或超時。

停機前持久化活躍實例的 `RuntimeState`，關閉 WebSocket，最後關閉 DB 與 Redis。

優雅停機不得丟失已下發但未回報的 pending 命令；這類命令由後續 `DeltaReport` 或人工審計流程處理。

## 第 7 章：不可推翻的技術決策

1. **複利前置條件：** 策略必須能清楚說明資金規模如何隨權益正回饋滾動。
2. **策略同構：** 回測與實盤呼叫同一個 `Step()`，禁止 `isBacktest` 分支。
3. **策略純函數：** 策略包禁止網路、資料庫、檔案 I/O、計時器與不可控外部狀態。
4. **SaaS 執行策略：** `Step()` 只在 SaaS 側執行，Agent 不含策略邏輯。
5. **OHLCV 外圈降級：** 現貨策略內核不依賴 `quant.Bar`，只吃降級後序列與快照。
6. **API Key 物理隔離：** 交易所憑證只存在於 `config.agent.yaml`，永不進 SaaS。
7. **GORM Code-First：** Go struct 是 schema 真源，只用 AutoMigrate。
8. **無量綱計算：** 價格相關計算使用比率、對數收益率或標準化特徵。
9. **倉位三態：** `DEAD_STACK`、`FLOATING`、`COLD_SEALED` 語義不得混用。
10. **底倉釋放只改帳本：** `DEAD_STACK → FLOATING` 不下發交易，只在 SaaS 側更新並審計。
11. **單一 Postgres：** 不分 Shell DB 與 Live DB，Redis 不承擔訊號傳遞。
12. **使用者介面零數學裸露：** 面向使用者的文字避免暴露內部術語與無上下文公式。
# 2026-06-18 修訂：Research 模組標的清單來源

Research 模組的研究標的不再是程式碼固定清單，而是由 SaaS DB 的 `ResearchInstrument` 透過 GORM AutoMigrate 管理。系統啟動時只寫入內建種子標的，使用者可在研究資料頁新增或停用標的；所有多商品選單必須讀取同一份啟用清單。

內建種子標的順序為：TQQQ、SQQQ、SOXL、SOXS、台灣加權指、標普 500、納斯達克 100、費城半導體、比特幣。Yahoo provider 標的預設支援 `1d`、`1h`、`1m`、`1w`、`1M`；Binance provider 標的預設支援 `1d`、`1h`、`15m`、`5m`、`1m`、`1s`、`1w`、`1M`。

行情資料自動更新由 SaaS 排程呼叫 provider 拉取，不使用交易所憑證，不寫入任何使用者 API key。資料新鮮度總覽必須能依市場快速檢查各標的、各週期是否更新到理論最新 bar。
